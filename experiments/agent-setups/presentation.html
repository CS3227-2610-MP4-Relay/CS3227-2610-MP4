An experiment on our own project · October 2026

How should we work
with AI coding agents?

We ran 118 coding sessions on four real Relay tasks, to find out what a way of working costs and what it buys. Then we used what we learned to build a better one.

The setting

Relay is written mostly
by AI agents

Relay is the beta-testing portal our team is building in Django. We write the specifications and make the decisions. AI coding agents, programs like Claude Code that read the code, write changes and run the tests, do most of the typing.

People

decide what to build, and approve every merge.

Agents

write the tests, the code and the docs, then check each other's work.

The problem

There are many other ways
to work with agents

Fewer agents

One agent does it all

No hand-offs. But who checks its work?

Cheaper models

Sonnet, Haiku, DeepSeek

A fraction of the price. Are they good enough?

Popular plugins

Methods and add-ons

superpowers, spec-kit and OpenSpec bring a method; caveman, ponytail and headroom promise to save tokens.

Each has its fans. None had been tested on our own work, so we didn't know which would actually help.

What we set out to learn

Three questions

  1. Does the way you set up agents change the quality of the code they write?
  2. What does each setup cost, in money and in time?
  3. Can we design one setup that does well with any model, in any tool, on any project?

Before we start

A few words we'll use

Session

One agent working through a task. It remembers what it has read so far.

Subagent

A fresh agent that a session starts for part of the work. It begins with an empty memory.

Hand-off

Passing work to another agent, which then has to read everything again.

Reviewer

An agent that checks finished work without changing it.

Models

Opus is the strongest and priciest. Sonnet sits in the middle. Haiku and DeepSeek are cheap.

Tools

Claude Code, Codex and Hermes: programs that let a model work in a repository.

The experiment

A fair race

The same start

  • the same task, with the team's decisions given up front
  • the same tool version and permissions, and no web access
  • its own clean copy of the code and its own test database
  • compared only with runs on the same model

The same finish line

  • hidden tests, written before any run ended
  • the project's full set of checks
  • five planted bugs its own tests had to catch
  • a blind review by a fresh agent that didn't know the setup

118 runs in all. We wrote each task's rules down before its first run ended.

Meet the setup

A small package that tells any agent
how to make one change well

You install it into a repository. From then on, whichever agent you use reads it and follows the same steps: one agent builds the change, and one independent reviewer checks it before a person merges.

Any tool

Claude Code, Codex, Hermes, or anything that reads AGENTS.md.

Any model

The same steps for every model. It never needs to know how strong the model is.

Any project

New or existing. One short settings file holds everything specific to a project.

Throughout

Two rules for every step

Only measured numbers

Every test count, line count and commit in the plan or report comes from a command run in this session. If it wasn't measured, the report says so. A review is claimed only if a separate reviewer did it.

Every report that stated a test count stated the one we measured.

Terse notes, full records

Working notes in the plan can be terse. Requirements, docs and the final report are written in full sentences, because people read them.

Borrowed from caveman, but only where nobody else has to read it.

0
Set up

the first time only

  • If the project file still has blanks, fill in what the repository already shows: its check commands, and its source, test and docs folders.
  • For anything it can't see, such as where requirements should live in a new project, propose the smallest default and ask the person to confirm.

Why

The same package has to start a new project as well as join an existing one. On an empty folder, Claude Code on Sonnet and Codex on DeepSeek each filled the file in, then built and reviewed a small tool, in about five minutes.

1
Prepare

read only what it touches

  • Note the starting commit and any unfinished work, and keep unrelated work safe.
  • Create a branch.
  • Read only the requirements and code the change touches.

Why

One session that reads the project once, and only the parts it needs, is where the saving over a team of agents comes from.

2
Specify

before any code

  • Update the requirements first, in the project's specs.
  • Write a short plan: the goal, the requirement delta (each requirement added, changed or removed), the person's decisions and where each lives, two to four checkpoints, and open questions.
  • Read the delta against the existing requirements: nothing contradicts them, and every decision is covered. Then commit.

Why

The spec is what tests and reviewers check against, so writing it first stops the code from quietly redefining the task. The delta comes from OpenSpec, and the read-through from spec-kit.

3
Build

checkpoint by checkpoint

  • Write the tests from the requirements, run them, and watch them fail.
  • Test each behaviour once, at the lowest level that shows it.
  • If a rule lists values, test every value. Mock only what lies outside the change.
  • Make the smallest complete change and commit it with its tests. Then break the new check once, to prove a test fails.

Why

A sampled test let a planted bug through, and a fully mocked test checked nothing. "Test each behaviour once" comes from ponytail: it keeps the tests lean.

4
Check

do the records still agree?

  • Every mention. Search the specs and docs for each name the change touched. Fix anything now untrue, including claims that a test covers something.
  • Every old test. If an old test's input is now refused, keep what it tested. Don't swap in an allowed input.
  • Every decision. Each is built and tested, or written in its home. Record as accepted only what a person decided.

Why

Most serious review findings were one of these three gaps: records drifting apart, not broken code.

5
Freeze

one final, full check

  • Run the project's full checks once, on the final commit.
  • Write down the exact result.
  • From here, the change is a fixed range of commits for the reviewer.

Why

Running everything once at the end, instead of after every step, saves time. A frozen range means the reviewer checks exactly what will merge.

6
Review

fresh eyes, hands off

  • A separate, read-only agent gets only the request, the decisions, the commit range and the check results.
  • It checks behaviour, whether the tests could fail, every mention and decision, scope and size, and security.
  • High-risk areas, such as sign-in, permissions, AI calls or deployment, also get a security reviewer.
  • It runs on the session's own model, unless AGENT_REVIEW_MODEL names another. If the tool can't start a separate agent, a person reviews instead.

Why

A model checking its own work missed scope problems. Left to choose, a cheap model hired an expensive reviewer and tripled its cost.

7
Repair & report

then hand back

  • Fix every Medium or High finding. Re-run the checks, and have the same kind of reviewer look at just the repair.
  • Stop after two rounds, or at anything that needs a person's decision.
  • End with a report: the commits, the requirement delta with the test for each requirement, the checks actually run, each finding and its fix, and what's still open.

Why

Endless repair loops cost more than they find. A report built only from commands that were really run is one a person can trust.

Any model

One workflow for every model

Version 6 had a strict profile for weaker models and a lighter one for strong ones. But a setup can't tell which model it is running on, or whether that model is weak.

So version 7 dropped the profiles, and kept for every model the safeguards that had helped the weaker ones: tests seen failing first, a check that they can fail, and numbers only from commands actually run.

The one switch

AGENT_REVIEW_MODEL runs the reviewer on a model you choose, at a cost. Without it, the reviewer uses the session's model, and the agent never picks one itself.

The exception

Where it doesn't save money

On Opus, the hardest task drew two full repair rounds, and each reviewer pass costs Opus prices. With Haiku, MP4's extra agents are cheap too.

There, what it buys is the same steps in any tool, and an independent review. The saving comes from the cheaper model, which it makes safe to use.

A version that didn't pay

More rules made it dearer, not better

Version 8 added four rules, each answering a review finding on the vaguer task. On that task it cost more on every model; on Sonnet it took three times as many turns.

Its reviews were no cleaner: the problem its main rule targeted came back on Opus and Sonnet. So we kept version 7.

PART FOUR

What this
means for us

Takeaways

If you work with coding agents

  1. Build in one session.
  2. Keep exactly one independent reviewer.
  3. Try the cheaper model first, even for hard work.
  4. Before review, check that specs, tests and decisions agree.
  5. Write the project's facts down once.
  6. Add a rule only when it pays: more rules made runs dearer, not better.

Takeaways

Skip these, or test them first

  • Token-saving add-ons and proxies: little gain, and a proxy sees your key.
  • More agent roles: they cost more and found nothing extra.
  • Teams of subagents in unattended runs: they can stop halfway.
  • Letting the model choose its own reviewer.
  • Trusting one task: the add-ons looked great on the first one.

Be careful with

What this experiment can't tell you

  • Four tasks, in one Django project, with the team's decisions made up front.
  • Quality hit the ceiling on every task, so this mostly measures cost, time and review findings.
  • One to three runs per setup and task, so only large differences count.
  • Costs are list prices from each tool's own report. A subscription bills differently.

Next

What we'd do next

  1. Try the setup on a second project, and on work with no decisions made up front.
  2. Plant gaps in the specs, not only bugs in the code, to measure what review catches.
  3. Repeat the newest version's runs before trusting its small differences.
