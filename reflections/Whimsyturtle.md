# Multi-Agent SE and Context Engineering Reflections: Whimsyturtle

After [MP3](https://github.com/CS3227-2610-MP3-Deskmate/CS3227-2610-MP3/blob/main/reflections/Whimsyturtle/reflection.md#lessons-i-learnt), I wanted to keep independent review for risky work while spending less effort passing small changes between agents. I also wanted to measure resource use properly and try our AI features with real model responses earlier. Relay, our beta-testing portal, gave me a chance to work on all three. Its AI helps teams draft test cases and helps testers improve their written observations. Building it also made me revisit a more uncomfortable question: how much could I trust the workflow I had designed?

## Multi-Agent SE

### Designing the Coordination Pattern

I simplified the roles we used in MP3. The main coding agent, or coordinator, planned the work and brought the results together. A builder wrote the specifications, code and tests, while separate agents checked correctness and security. This combined Week 8's **Orchestrator-Subagent** and **Generator-Verifier** patterns with **Spec-Driven Development**: agree on the behaviour before implementing it. Reviewers checked a version of the code that stayed unchanged during review, and only the coordinator managed Git.

Giving the builder both code and tests meant fewer handoffs, but I was giving up a separation I had valued in MP3. In a controlled workflow test, deliberately weakening an assertion made a failing test pass without fixing the code. Our file restrictions allowed that edit; comparing the changes exposed it. I learned that limiting which files an agent can edit says little about whether its edits are good. I still needed to see the test fail first, understand changes to assertions, and have someone independently inspect them. ([Logs 001](../logs/Whimsyturtle/001-initialize-relay-scaffold-and-log-usage.md) and [030](../logs/Whimsyturtle/030-test-development-workflow-controls.md); [builder](../workflow/agents/builder.md); [verifier](../workflow/agents/verifier.md))

### Verifying That Coordination Actually Happened

When we added tracking for AI request usage and response times, I could follow the coordination in the logs. The coordinator gave the builder the relevant requirements, files and limits, then reused that builder through implementation and documentation. Because the change affected shared AI code, both correctness and security reviewers checked the same completed version. The coordinator managed Git and the test database, and the handoffs recorded checks, findings and next steps. That gave me something concrete to inspect. In an earlier browser-testing task, however, the coordinator reused sessions even though I had asked for fresh agents for each user journey. I accepted the implementation, but it reminded me to check how the work was done as well as what was delivered. ([Logs 024](../logs/Whimsyturtle/024-record-llm-usage-and-latency.md#agent-runs) and [011](../logs/Whimsyturtle/011-add-playwright-browser-journeys.md#decisions-and-corrections))

I also wanted to know whether our restrictions would actually stop an edit. I authorised an attempt to change a protected file in a throwaway checkout. Codex and Claude's pre-edit checks blocked the attempts, and the files stayed unchanged. Seeing that happen was more useful than an agent saying it would obey the rules. ([Log 043: workflow checks](../logs/Whimsyturtle/043-verify-native-workflow-hooks.md))

The same concern carried over to testing the app. In MP3, tests could pass even if the loading indicator's JavaScript was removed. For Relay, we used Playwright to exercise the app in a real browser and checked that a loading message appeared while an AI response was deliberately delayed. I wanted the test to catch the missing behaviour at the moment a user would notice it. We still had to repair browser timing issues, but this was a more useful check than waiting for the final page to appear. ([Logs 011](../logs/Whimsyturtle/011-add-playwright-browser-journeys.md) and [036](../logs/Whimsyturtle/036-repair-ui-journeys.md))

### Agents Waiting or Being Blocked

Some waiting was built into the workflow: reviewers had to wait for the builder to finish. Reusing one builder across five rounds of work on tester availability helped it retain context without several agents editing the same files. Other delays came from assignments that overlooked tool access. During the context experiment, a worker could not check the coordinator's running command or read its temporary data. The coordinator had to keep checking the command and pass answers to the worker in batches. Next time, I would check which tools a worker can actually access before handing it the job. ([Logs 013](../logs/Whimsyturtle/013-build-tester-availability.md) and [050](../logs/Whimsyturtle/050-run-full-context-comparison.md#agent-runs))

Shared resources caused more avoidable problems. During deployment work, a reviewer and the coordinator ran tests against the same test database, causing 91 setup errors. Later, agents in separate Git worktrees tried to use the same database port. Week 8's **workspace isolation** became very concrete here: separate copies of the files still shared the machine's ports and databases. I needed to assign ownership of those resources or schedule the runs. ([Logs 012](../logs/Whimsyturtle/012-prepare-vercel-and-neon-production-delivery.md#agent-runs) and [042: accessible errors](../logs/Whimsyturtle/042-fix-accessible-result-errors.md#problems))

### Retries and Repeated Work

During the AI usage-tracking work, the security reviewer reran an unchanged 526-test suite. It was already running when the coordinator asked it to reuse the earlier results. That was work we could have avoided. By contrast, repeating the same model request was useful in our experiments: ten of twelve groups of five requests produced different raw replies even with temperature set to zero, the setting intended to reduce randomness. That convinced me to use repeated trials in the later comparison. I now separate reruns caused by failures, unnecessary duplication, and deliberate experimental repeats. Earlier check results are useful while the code, inputs and environment stay the same. ([Logs 024](../logs/Whimsyturtle/024-record-llm-usage-and-latency.md) and [047](../logs/Whimsyturtle/047-test-temperature-zero-repeatability.md); [repeatability results](../experiments/app-context/README.md#read-the-results))

### Resolving Disagreements

When we tested an AI grader against prepared examples, it agreed with 97 of 98 reference labels. The disagreement was about a reply telling a tester to mark or submit a result. Was that only overstepping the AI's advisory role, or was it also inventing facts? Another agent found both interpretations understandable. I accepted a clearer rule: telling the tester to submit oversteps the role; it also counts as inventing facts if the reply claims unsupported product behaviour. We kept the original score rather than turning it into perfect agreement after changing the rule. ([Logs 049](../logs/Whimsyturtle/049-calibrate-constructed-answer-grading.md) and [050](../logs/Whimsyturtle/050-run-full-context-comparison.md#requests))

This helped me understand a limitation of **Generator-Verifier**. A reviewer needs a clear standard to check against. Asking another model helped reveal the ambiguity, but I still had to decide what behaviour we wanted. That was a practical example of **human oversight**.

### Whether the Benefits Outweighed the Costs

Review earned its place when it caught a mistake the earlier checks had missed. During Django setup, the security reviewer found that an inherited database setting could redirect our test connection. Later, a fix for stale form submissions passed 3,182 tests and a correctness review, yet security review found a deployment problem: a database change removed a default that the older application version still needed to save data. We reproduced that failure and kept the default. The reviewer brought a way of thinking about deployment that our existing tests had missed. ([Logs 006](../logs/Whimsyturtle/006-build-django-foundation-and-ci.md) and [045](../logs/Whimsyturtle/045-prevent-stale-result-overwrites.md#agent-runs))

I was less happy to see the coordinator invent a 200-line commit limit, repeating an unrequested size rule from MP3. The independent reviewers missed it too, and I had to challenge it. I had already concluded in MP3 that I should check the orchestrator; MP4 showed me I was still relying too much on written instructions to solve that problem. Specialist review was worth keeping for these concrete risks. Whether the whole workflow saved time remains an open question, since I did not compare the same development tasks with and without multiple agents.

### When I Would Use Multiple Agents

I would use a second agent when a different perspective could catch an expensive mistake: incorrect permissions, unsafe AI replies, weak tests or deployment failures. Our live prompt-injection tests, where we put malicious instructions into app data, showed why that perspective matters. One answer followed the attack without repeating its identifying phrase; another repeated a phrase without carrying out the harmful request. Checking for a marker alone could misjudge both. I needed someone to read what the answer actually meant. The first prompt revision also left contamination in the replies, so testing with real responses remained necessary. ([Logs 027](../logs/Whimsyturtle/027-fix-live-drafting-reply-schema.md) and [028](../logs/Whimsyturtle/028-reduce-feedback-prompt-contamination.md))

Those failures also made me value the limits around the AI. Feedback receives only the tester's saved observation and the test context they are allowed to access, and returns questions without changing the result. Choosing to use a generated test draft only fills in the normal form; the user still decides what to save. Week 6's **access control** and **human oversight** became concrete here. I needed to limit what the model could see and do, while still checking whether its advice was misleading. ([Logs 021](../logs/Whimsyturtle/021-build-saved-observation-feedback.md) and [027](../logs/Whimsyturtle/027-fix-live-drafting-reply-schema.md))

For a cosmetic edit, I would usually keep the process lighter. Extra agents each have to load context, and that effort needs a purpose. I also questioned our limit of eight acceptance criteria per feature batch when I saw requirements being packed together to fit it. I preferred guidance based on whether the change was easy to review. Week 9.2's **valuemaxxing** captures what I took from this: choose the process for the useful work it adds. ([Log 007](../logs/Whimsyturtle/007-investigate-the-eight-criterion-slice-budget.md); [workflow tiers](../workflow/skills/slice.md))

## Context Engineering and Resource-aware Use

### Engineering Instructions and Skills

I used the repository's instructions, role files and skills to tell agents where to find requirements, what they could change and what finishing a task meant. I revised the workflow after an agent completed the Django work but stopped before the expected commits, draft pull request and GitHub checks. Week 9.1's **right altitude** was useful here: instructions needed enough detail to make completion clear, without arbitrary rules like the commit-size limit. ([Log 006](../logs/Whimsyturtle/006-build-django-foundation-and-ci.md))

Our app prompts had a more basic omission. All six early live replies from the test-drafting feature failed format validation, including the reply to an ordinary, harmless request. The prompt referred to a JSON format without specifying its field names and types. After supplying those details and fixing a validation check, replies could pass validation, but some still invented product behaviour. This repeated a lesson from MP3's article-matching feature: specifications and fake-model tests can agree with each other while missing what happens with a real model. I should have tried real responses earlier. ([Logs 026](../logs/Whimsyturtle/026-scope-live-injection-evaluation.md) and [027](../logs/Whimsyturtle/027-fix-live-drafting-reply-schema.md))

### Supplying Context Up Front or Retrieving It

I found it useful to give agents the goal, agreed decisions, acceptance criteria and exact version to work on up front. They could then read the relevant files as needed. This is Week 9.1's **just-in-time retrieval**: the assignment carries decisions that would change the task, and links point to the supporting detail. ([Log 014](../logs/Whimsyturtle/014-build-tester-result-submission.md#agent-runs))

I also became more deliberate about what an evaluator should see. My MP3 handoff experiment used one task, let the grader know the handoff format, and added sessions after I had seen the first results. For MP4's separate experiment on app context, I fixed the inputs and schedule first, repeated requests, and gave fresh graders the answers and marking rules without model or condition labels. I wanted their judgments to depend on the answer rather than expectations about the model. ([MP3 experiment](https://github.com/CS3227-2610-MP3-Deskmate/CS3227-2610-MP3/blob/main/reflections/Whimsyturtle/reflection.md#3-what-one-agent-must-pass-to-the-next); [log 050](../logs/Whimsyturtle/050-run-full-context-comparison.md#agent-runs))

### Organising Context So Instructions Remain Findable

I kept MP2's **one home per fact** approach. Product requirements go in specifications, plans link to them, and guides explain the built app. The root instructions point agents to the right documents. This gives **progressive loading** a practical form: start with a map, then open the detail needed for the job. When we reorganised the Developer Guide, it went from 4,042 to 1,125 words, with all 16 shell-command blocks preserved in a separate operations guide. The setup overview became shorter without throwing away the commands someone would need later. ([Fact ownership](../AGENTS.md#one-home-per-fact); [log 038](../logs/Whimsyturtle/038-restructure-developer-guide.md#agent-runs))

Better organisation still needed follow-through. During a later repair to the tester screens, I had to remind the coordinator about creating a branch and committing completed units as it worked. Splitting the changes into commits afterwards did not mean it had followed those checkpoints. I wanted the log to preserve that distinction, because otherwise I could easily mistake a tidy history for a process that had worked as intended. ([Log 037](../logs/Whimsyturtle/037-fix-tester-results-and-feedback.md))

### Recording an Efficient Handoff

In MP3, both checklist and prose handoffs lost roughly half the facts the next agent needed, and one checklist buried an unresolved decision as an assumption. For Relay, I focused on asking for the goal, current code version, agreed decisions, changed files, checks actually run, open problems and next action. Links could carry the detailed requirements. ([MP3 findings](https://github.com/CS3227-2610-MP3-Deskmate/CS3227-2610-MP3/blob/main/reflections/Whimsyturtle/reflection.md#3-what-one-agent-must-pass-to-the-next); [handoff format](../AGENTS.md#handoff))

The most useful handoff is honest about what remains unfinished. One log kept three failing Windows tests visible even though focused checks and reviews had passed. The next session needed to know those failures were still there. That is what Week 9.1's **structured note taking** means to me: save the decisions and evidence needed to continue, including the awkward parts. ([Log 037](../logs/Whimsyturtle/037-fix-tester-results-and-feedback.md#problems))

### When More Context Made Results Worse

MP3 made me worry about leaving information out. MP4 made me more careful about putting information in. I compared relevant context, extra app-related clutter and off-topic material while keeping the JSON fields the same. Across twelve scenarios, three requested models and five repeats per combination, Qwen's test drafts passed every check in 29/30 relevant-only attempts but only 20/30 with app clutter. One Llama answer even turned unrelated background topics into test cases. Seeing the distraction appear in the answer made **context pollution** much less abstract to me. ([Full comparison results](../experiments/app-context/README.md#read-the-results); [log 050](../logs/Whimsyturtle/050-run-full-context-comparison.md))

The extra context also added about 574–594 input tokens per call. For Qwen drafting, app clutter cost about 580 extra tokens while fewer answers passed. Yet one model, x-test-2, improved its observation-feedback results from 5/30 to 9/30 with clutter. I would now choose context for the specific task and model instead of assuming that shorter is always better. These were twelve synthetic scenarios graded by models, so I would want human checks and real user cases before generalising the results.

The feedback results also made me question what I was counting as helpful. In each of two reports that were already complete, all 43 replies that passed format validation still asked unnecessary questions. I had focused on whether the AI could find missing details; I also needed to check whether it could recognise that nothing was missing. This reminded me of Week 5's **no-change accuracy**: sometimes the correct response is to leave things alone. ([Full comparison results](../experiments/app-context/README.md#read-the-results))

I also learned that a context budget has to fit legitimate input. A feedback request using the largest valid fields could reach 32,249 characters after adding the instructions and formatting the data as JSON. We raised the shared allowance to 32,768 characters. I had to count what we actually sent to the model, including extra characters used to represent quotes and backslashes. This made Week 9.1's **context engineering** more concrete: keep the information needed for the task and make room for it within the limit. ([Log 039: feedback inputs](../logs/Whimsyturtle/039-cover-maximum-feedback-inputs.md#decisions-and-corrections))

### Choosing Models and Reasoning Effort

I asked for explicit settings: OpenAI's GPT-6.1 Sol at medium reasoning effort for implementation and high effort for correctness and security review. Making those choices visible gave me something to evaluate and revise. I had not yet measured which settings worked best. ([Log 005](../logs/Whimsyturtle/005-set-explicit-subagent-model-defaults.md))

Later, low-effort Sol graders agreed with 97/98 reference labels across 24 prepared answers. That made low effort worth considering for tightly defined grading work. The references and reviews came from the same model family, though, and lacked human validation; I would check real answers before relying on that result more broadly. I also learned to record which model and effort actually ran. A setting in a configuration file was not enough, especially when we could not check Claude's command-line tool. ([Log 049](../logs/Whimsyturtle/049-calibrate-constructed-answer-grading.md))

### Cache Misses and What the Measurements Showed

Week 9.2's **prompt caching** gave me a reason to keep stable instructions before changing task details and reuse a builder while it was still doing related work. During the AI usage-tracking task, 14.64 million of 15.01 million input tokens came from cache, about 97.5%. That was substantial reuse, but cached tokens still counted in the total. We did not compare against an uncached run, so I cannot put a saving on our prompt organisation. I would keep related work together and measure that comparison before making stronger claims. ([Log 024](../logs/Whimsyturtle/024-record-llm-usage-and-latency.md); [accounting definitions](../workflow/README.md#token-reporting))

### Internal Reasoning and Persisted State

The same task recorded 10,732 reasoning tokens: 22.7% of output tokens, but only 0.071% of all recorded tokens. That changed where I would look for savings. Repeated input, including cached input, dominated this run. Week 9.2's **persisted reasoning** suggests saving useful analysis so later sessions can avoid repeating it. Our plans and handoffs saved explicit decisions and findings, which I would keep doing so the next agent could pick up those decisions without working through them again. ([Log 024](../logs/Whimsyturtle/024-record-llm-usage-and-latency.md); [token definitions](../workflow/README.md#token-reporting))

### Other Ways I Monitored Resource Use

Before trusting our token tables, I asked for an audit of earlier measurements. Replaying the original sources reproduced all seventeen totals, but finding previously omitted sessions increased several totals. The work had not suddenly become less efficient; we had been counting less of it. The collector also needed fixes for incomplete counters and duplicated history. This made **traceability** feel like part of the experiment itself. I now want a baseline at the start, coverage of the coordinator and delegated sessions, and clear gaps wherever usage is unavailable. ([Logs 017](../logs/Whimsyturtle/017-investigate-codex-token-accounting-gaps.md) and [018](../logs/Whimsyturtle/018-audit-historical-token-counts.md))

### Which Tasks Consumed the Most Tokens

Deployment and experiment coordination stood out. The historical audit could count about 95.9 million deployment tokens, with a complete total unavailable. The full context comparison recorded 59.0 million tokens for development and grading during its measurement window. The main grading stage alone used 9.87 million. Assessing AI output had become a sizeable task of its own. ([Logs 018](../logs/Whimsyturtle/018-audit-historical-token-counts.md) and [050](../logs/Whimsyturtle/050-run-full-context-comparison.md))

We reused a grade when an answer was exactly identical within the same experiment condition, while still counting how often that answer appeared. This avoided grading the same thing again. Repeated reading and grading are where I would look next. I would also keep coding-agent usage separate from the school-hosted models generating the app's answers, so I could see which part of the work was consuming the resources.
