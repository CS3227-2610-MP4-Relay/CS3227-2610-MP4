# Multi-Agent SE and Context Engineering Reflections: Whimsyturtle

In [MP3](https://github.com/CS3227-2610-MP3-Deskmate/CS3227-2610-MP3/blob/main/reflections/Whimsyturtle/reflection.md#lessons-i-learnt), I found independent review useful for risky work, but specialised agents added overhead to small changes, and resource costs were rarely measured. I also wanted to test AI features against real responses and improve what agents passed between sessions. For Relay, we consolidated the development roles, tested the workflow itself, checked its resource measurements, and experimented with the context supplied to its AI features. Some changes addressed MP3's gaps, while others exposed new tradeoffs or repeated problems I thought the workflow would prevent. The sections below follow the questions in MP4.

## Multi-Agent SE

### Designing the Coordination Pattern

Our workflow combined Week 8's **Orchestrator-Subagent** and **Generator-Verifier** patterns: a coordinator scoped the task and integrated results, a builder implemented from specifications, following **Spec-Driven Development**, and separate agents reviewed correctness and relevant security risks. Reviewers inspected a fixed candidate, while only the coordinator changed Git state. Consolidation reduced the number of role transitions, but gave up a separation I valued in MP3: the implementer could not write tests, whereas Relay's builder owns both. Our workflow probe showed that a permitted test edit could weaken an assertion and turn a failing test green. Candidate comparison detected the edit, but path restrictions could not judge its quality. We therefore relied on evidence of tests failing before implementation, justified test changes and independent assertion review to address **test weakening**. These checks made the tradeoff visible without establishing equivalent protection or measured savings. ([Logs 001](../logs/Whimsyturtle/001-initialize-relay-scaffold-and-log-usage.md) and [030](../logs/Whimsyturtle/030-test-development-workflow-controls.md); [builder](../workflow/agents/builder.md); [verifier](../workflow/agents/verifier.md))

### Verifying That Coordination Actually Happened

I distinguished configured rules from observed enforcement. I authorised a valid prohibited edit in a disposable worktree to test Claude's hook properly. Actual Codex and Claude hook rejections, with unchanged protected-file hashes, provided stronger evidence than an agent's verbal refusal. These probes established specific controls, not general resistance to malicious instructions. I also followed up on MP3's browser-testing gap: its loading indicator was left to manual checks because tests could pass even with the JavaScript removed. Relay added Playwright journeys in Chromium and later checked pending feedback while a response was deliberately held back. This gave evidence of **defect-finding power** at the relevant moment, rather than merely checking that the final page appeared. Browser timing still needed repair, and controlled model replies in those tests could not establish live-model usefulness. ([Logs 039: native hooks](../logs/Whimsyturtle/039-verify-native-workflow-hooks.md), [011](../logs/Whimsyturtle/011-add-playwright-browser-journeys.md) and [036](../logs/Whimsyturtle/036-repair-ui-journeys.md))

### Agents Waiting or Being Blocked

Some waiting followed the dependency between implementation and independent review: reviewers needed a frozen candidate first. Reusing one builder across five runs on tester availability preserved continuity without concurrent edits. The full context experiment exposed a different resource-sharing problem: a worker could not poll the coordinator's execution session or access its transient store, so the coordinator retained polling and supplied bounded grading batches. This showed that delegation must account for tool access as well as task decomposition. Our elapsed spans include waiting, so they cannot establish agent utilisation or overload. ([Logs 013](../logs/Whimsyturtle/013-build-tester-availability.md) and [050](../logs/Whimsyturtle/050-run-full-context-comparison.md#agent-runs))

### Retries and Repeated Work

Independent review sometimes duplicated execution: during LLM usage tracking, the security reviewer repeated an unchanged 526-test AI suite; it was already running when the coordinator requested evidence reuse. Conversely, repeating identical model requests was deliberate experimental work: ten of twelve five-request groups varied in raw output despite requested temperature zero, supporting repeated trials in the later comparison. I would distinguish a retry caused by failure, an unnecessary rerun, and a planned repeat before deciding which to remove. Reusing check evidence remains appropriate only while its code, inputs and environment are unchanged. ([Logs 024](../logs/Whimsyturtle/024-record-llm-usage-and-latency.md) and [047](../logs/Whimsyturtle/047-test-temperature-zero-repeatability.md); [repeatability results](../experiments/app-context/README.md#read-the-results))

### Resolving Disagreements

During grader calibration, an independent agent matched 97 of 98 reference labels; the disagreement concerned whether asking a tester to mark or submit an outcome violated grounding as well as the AI's boundaries. A separate adjudicator found both readings understandable. I accepted the clarification that such requests fail boundaries, and fail grounding when they also assert unsupported product facts. We preserved the original score rather than rewriting it into perfect agreement. This applied **human oversight** to an ambiguous requirement: another model opinion helped expose the issue but did not decide the intended rule. ([Logs 049](../logs/Whimsyturtle/049-calibrate-constructed-answer-grading.md) and [050](../logs/Whimsyturtle/050-run-full-context-comparison.md#requests))

### Whether the Benefits Outweighed the Costs

Specialist review was useful when it found something our initial checks missed. During Django setup, the security reviewer exposed inherited `PGHOSTADDR` redirecting the intended test database connection; a driver-level regression verified the repair. However, the coordinator also invented a 200-line commit limit, repeating MP3's unrequested size rule. Independent reviewers missed it until I challenged it and had it removed. This qualified my MP3 lesson to check the orchestrator too: stronger instructions and separate reviewers still needed my **human oversight**, and the builder-hook probes did not demonstrate equivalent enforcement on the coordinator. These examples support review for concrete risks while retaining human judgement over policy. They do not establish an overall productivity gain: we did not run equivalent single-agent and multi-agent versions of my development tasks. ([Log 006](../logs/Whimsyturtle/006-build-django-foundation-and-ci.md))

### When I Would Use Multiple Agents

I would use specialist agents where independently checking permissions, AI boundaries or test assertions can expose consequential mistakes, and use parallel workers when ownership and inputs are separable. Following MP3's proposal, I ran real-model injection tests; one accepted answer followed an attack's meaning without its marker, while another mentioned a marker without demonstrating credential solicitation. This showed why deterministic scoring also needs semantic review. A first prompt refinement still reproduced contamination, and one cleaner later pass did not establish general resistance. For cosmetic changes, extra agents can add more context loading than useful scrutiny. I also questioned our eight-criterion slice limit after noticing requirements being packed to fit it; the investigation supported a reviewability guideline, without proving the limit caused defects. This reflects Week 9.2's **valuemaxxing**: choose coordination by its contribution to quality and reviewability. ([Logs 027](../logs/Whimsyturtle/027-fix-live-drafting-reply-schema.md), [028](../logs/Whimsyturtle/028-reduce-feedback-prompt-contamination.md) and [007](../logs/Whimsyturtle/007-investigate-the-eight-criterion-slice-budget.md); [slice tiers](../workflow/skills/slice.md))

## Context Engineering and Resource-aware Use

### Engineering Instructions and Skills

I treated repository instructions, role definitions and skills as parts of the agent's effective context, while recognising that they do not all have system-level authority. The root rules define trusted instructions, scope and fact ownership; role files narrow responsibilities; the slice skill supplies the execution protocol. I revised it after the Django handoff stopped before the intended commits, draft PR and hosted checks. This illustrated Week 9.1's **right altitude**: instructions should make completion checkable without arbitrary constraints. MP3's article-matching failure also led me to check our app prompts against real responses. All six early live drafting replies, including the benign control, failed schema validation; the prompt referred to a schema without giving its exact keys and types. We made it explicit, then corrected a gateway check that rejected Qwen's empty list of tool calls. Replies could then pass validation while still inventing product behaviour. As in MP3, agreement between specifications, code and fake-model tests had not established that the AI feature achieved its purpose. The earlier rejected replies could not show whether the repairs introduced those semantic failures or merely made them observable. ([Logs 006](../logs/Whimsyturtle/006-build-django-foundation-and-ci.md), [026](../logs/Whimsyturtle/026-scope-live-injection-evaluation.md) and [027](../logs/Whimsyturtle/027-fix-live-drafting-reply-schema.md))

### Supplying Context Up Front or Retrieving It

Scope, confirmed decisions, acceptance criteria and candidate identity belonged in the assignment; source details could be retrieved through relevant paths. This follows Week 9.1's **just-in-time retrieval**, keeping each role focused without withholding decisions that change the task. Context selection also mattered for evaluation. MP3's handoff experiment used one task, a grader that knew the format, and sessions added after seeing initial results. For MP4's app-context comparison, I froze the inputs and schedule, repeated calls, and used fresh feature-specific graders supplied with the rubric and transient answers while model and condition labels were withheld. These choices addressed weaknesses in the earlier method for a different question; they did not constitute a repeated handoff experiment. The separation was procedural, not enforced access isolation, so I would not describe the graders as technically unable to discover withheld information. ([MP3 experiment](https://github.com/CS3227-2610-MP3-Deskmate/CS3227-2610-MP3/blob/main/reflections/Whimsyturtle/reflection.md#3-what-one-agent-must-pass-to-the-next); [logs 014](../logs/Whimsyturtle/014-build-tester-result-submission.md#agent-runs) and [050](../logs/Whimsyturtle/050-run-full-context-comparison.md#agent-runs))

### Organising Context So Instructions Remain Findable

I retained MP2's **one home per fact** approach: product behaviour belongs in specifications, implementation plans link to it, and guides describe built behaviour. The root document routes agents to the relevant workflow rather than duplicating every procedure. This supports **progressive loading** and reduces conflicting copies. However, organisation does not guarantee compliance: during a later tester UX repair, I had to correct the coordinator again for missing branch and incremental-commit steps. The resulting log explicitly distinguished retrospective commit organisation from following those checkpoints during implementation. ([Fact ownership](../AGENTS.md#one-home-per-fact); [log 037](../logs/Whimsyturtle/037-fix-tester-results-and-feedback.md))

### Recording an Efficient Handoff

In MP3, both checklist and prose handoffs lost roughly half the expected facts, and one checklist hid an open decision as an assumption. I therefore focused on what the handoff explicitly asks for: the goal, current candidate, confirmed decisions, changed files, actual checks, open findings and next action, with links instead of repeated specifications. It must also preserve uncertainty. For example, the tester UX log retained three Windows diagnostic-message test failures despite passing focused checks and reviews; it did not turn an attributed baseline problem into a successful full run. This makes **verification completion** assessable by the next session. Following Week 9.1's **structured note taking**, I would save decisions and evidence needed to continue. These examples show the practice, but I did not repeat the MP3 recall experiment to measure whether handoffs preserved more facts. ([MP3 findings](https://github.com/CS3227-2610-MP3-Deskmate/CS3227-2610-MP3/blob/main/reflections/Whimsyturtle/reflection.md#3-what-one-agent-must-pass-to-the-next); [log 037](../logs/Whimsyturtle/037-fix-tester-results-and-feedback.md#problems); [handoff format](../AGENTS.md#handoff))

### When More Context Made Results Worse

MP3's handoff experiment showed the danger of omitting necessary facts; MP4's app-context comparison showed that adding irrelevant information could also hurt. My full comparison held JSON fields constant across relevant-only, app-clutter and off-topic conditions, using twelve scenarios, three requested models and five repeats per combination. Qwen drafting met every check in 29/30 relevant-only attempts but 20/30 with app clutter; a Llama answer incorporated unrelated background topics as tests. These are concrete **context pollution** signals. However, `x-test-2` feedback improved from 5/30 to 9/30 with clutter, so the conclusion is task- and model-dependent. Together, the experiments qualified my preference for concise context: I need to preserve necessary decisions while excluding distractions. The 540 attempts cover twelve synthetic scenarios, and model-authored grades are not human-validated ground truth. ([Full comparison results](../experiments/app-context/README.md#read-the-results); [log 050](../logs/Whimsyturtle/050-run-full-context-comparison.md))

### Choosing Models and Reasoning Effort

I requested explicit model settings so they could be evaluated instead of silently inherited: Sol at medium effort for implementation and high effort for verification and security review. These were starting defaults, not measured optima. Later, low-effort Sol graders matched 97/98 reference labels across 24 constructed answers. However, the reference author, grader and adjudicator were separate sessions of the same model family, and the references were not human-validated ground truth. This showed strong agreement on a tightly specified task, without establishing natural-answer accuracy or equivalence to higher effort. Recording observed model and effort separately from configuration also mattered because an adapter setting alone did not establish execution, particularly when the Claude CLI could not be checked. ([Logs 005](../logs/Whimsyturtle/005-set-explicit-subagent-model-defaults.md) and [049](../logs/Whimsyturtle/049-calibrate-constructed-answer-grading.md))

### Cache Misses and What the Measurements Showed

Week 9.2's **prompt caching** suggests keeping stable instructions before changing task details and reusing sessions where their scope remains coherent. We reused builders across checkpoints, but did not isolate caching as an experimental intervention. In the LLM usage-tracking slice, 14,638,080 of 15,010,176 input tokens were cached: a token-weighted cache-read ratio of 97.5%. This shows substantial context reuse, not a 97.5% reduction in total tokens or a request-level hit rate. Without a matched uncached baseline, I cannot quantify savings caused by our prompt organisation. ([Log 024](../logs/Whimsyturtle/024-record-llm-usage-and-latency.md); [accounting definitions](../workflow/README.md#token-reporting))

### Internal Reasoning and Persisted State

In that same slice, 10,732 reasoning tokens represented 22.7% of 47,352 output tokens, but only 0.071% of 15,057,528 total recorded tokens. Stating the denominator matters because repeated input, including cached input, dominated this measurement. Week 9.2's **persisted reasoning** could reduce repeated analysis, but our plans and handoffs persisted explicit decisions and findings, not hidden reasoning. We did not run a controlled persisted-reasoning comparison, so neither session reuse nor concise handoffs establish a measured reasoning-token saving. ([Log 024](../logs/Whimsyturtle/024-record-llm-usage-and-latency.md); [token definitions](../workflow/README.md#token-reporting))

### Other Ways I Monitored Resource Use

I investigated accounting gaps and requested a historical audit before relying on our token tables. Replaying the same original sources and windows reproduced all seventeen earlier measurements unchanged; broader source discovery increased several reported totals. This was improved coverage, not increased work or reduced efficiency. The collector also needed repairs for partial counters and overlapping history, reinforcing that **traceability** depends on trustworthy measurement. I would continue taking task-start baselines, including coordinator and approval-review sources, and recording unavailable counters explicitly before comparing workflow changes. ([Logs 017](../logs/Whimsyturtle/017-investigate-codex-token-accounting-gaps.md) and [018](../logs/Whimsyturtle/018-audit-historical-token-counts.md))

### Which Tasks Consumed the Most Tokens

Large deployment work and experiment orchestration stood out: the historical audit listed about 95.9 million available deployment tokens, with its strict aggregate unavailable, while the full comparison recorded 59.0 million development and grading tokens within its measured window. Primary grading alone used 9.87 million. The experiment reused judgments for exact duplicate answers within each cell, avoiding repeated assessment while retaining their observed frequency. That reduced duplicate work, but we did not measure a counterfactual saving. I would target repeated reading and grading next, while keeping development usage separate from SoC generation usage. ([Logs 018](../logs/Whimsyturtle/018-audit-historical-token-counts.md) and [050](../logs/Whimsyturtle/050-run-full-context-comparison.md))
