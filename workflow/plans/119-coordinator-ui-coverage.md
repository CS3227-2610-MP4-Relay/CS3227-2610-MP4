## Test design and evidence rules

- Reuse the [browser harness](../specs/TECHNICAL-SPEC.md#browser-verification): fresh synthetic accounts/context, real sign-in/forms/CSRF, bounded Playwright `expect`, no fixed sleeps, no live AI calls. Scope repeated actions to their intended criterion row or case disclosure; do not use global first/last controls to select a case.
- Preserve the native collapsed starting state until the test intentionally opens it. Use actual summary/Contents controls, not DOM mutation or an autouse expansion fixture. Use current visible labels and exact errors. Assert success appears once before reload, then assert persisted state after reload.
- Set up ORM fixtures before Playwright starts; inspect stored state after the page fixture stops, following existing yield-fixture patterns. Snapshot/refusal assertions must cover criteria/cases/link identities and build coverage, not just counts. Verify refused submissions create no row and successful retry produces exactly the intended change. Browser reloads provide intermediate persistence checks; teardown verifies final database invariants without bypassing Django async safety.
- Coverage-only red-before-code exception: these cases exercise already implemented requirements and may pass on their first run. Run them against unchanged runtime and record the actual result. Hidden/wrong-target action regressions fail at the scoped control or surviving-record checks; invalid writes fail reload/build/link checks; partial schema leakage fails absent-suggestion checks; premature adoption persistence fails the no-save/DB assertions. Do not manufacture failures or change runtime to create red evidence.
- Run focused checks with the confirmed fixed test settings/database and task-specific temporary/cache paths. No database tests or server startup are authorized for this preparation checkpoint; the coordinator is inspecting the environment first. New test/setup errors may be corrected and recorded, but a discovered runtime bug must be reported before repair.
