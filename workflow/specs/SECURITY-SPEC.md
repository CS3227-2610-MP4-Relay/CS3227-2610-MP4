# Security spec

Threats to Relay and to how it is built, and the controls against them. Controls below are implemented for the built criteria named in the [accounts](product/accounts.md), [rounds](product/rounds.md) and [results](product/results.md) status lines (ACC-1 to ACC-3, RND-1 to RND-8 with the shared AI gateway, RES-1 to RES-4), for [platform](product/platform.md) PLT-1's local, CI and release-job controls, PLT-2 and PLT-3, for the shared [access matrix](#sign-in-and-access-control) and for the [SEC-INJ-1](#sec-inj-1-operator-live-injection-measurement) measurement; other controls and their verification remain planned. Controls link to their acceptance criteria where specified, with verification added by the slices that implement them. No deployed security is claimed here.

## Secrets and settings

Threat: leaked keys, credentials or debug details expose data and production access.

- Keep secrets and personal data out of code, logs, fixtures and experiment evidence. Agents must not read secret files; see [`AGENTS.md`](../../AGENTS.md).
- Use separate development/test and production credentials and databases. Disable production debug mode and validate production configuration before startup.
- Tests use fixed non-secret values and a fake LLM provider. CI validation receives no production secrets. Production database TLS, host validation and error-detail handling must be specified and tested before deployment.

The PLT-1 foundation installs Django SecurityMiddleware, CommonMiddleware and CsrfViewMiddleware. Its original public route permits GET/HEAD and remains CSRF-exempt so other methods consistently return 405 even without a token; state-changing routes retain CSRF checks. Local settings require an environment secret key and restrict allowed hosts and the database host to loopback; test settings do not import runtime settings or read environment values. Debug defaults off locally and stays off in tests, using generic Django error pages. Production settings and TLS/host/proxy policy are specified under [Configuration](TECHNICAL-SPEC.md#configuration); their implementation and local checks do not establish hosted deployment security. CI's PostgreSQL service uses throwaway test values only.

Explicit database network addresses enforce loopback destinations despite inherited libpq environment overrides; see [configuration](TECHNICAL-SPEC.md#configuration).

## Sign-in and access control

Threat: a visitor or user accesses another role's operations, another workspace's records or another tester's private draft.

- Authorize every route and record lookup on the server before reading data or selecting AI context. Define role, workspace, ownership and state permissions for each operation.
- Use Django's authentication, password hashing and CSRF protections, including its `Origin` check. Sessions are server-side, get a new identifier at every sign-in, end at sign-out and expire at an absolute time; sign-in ignores redirect targets ([ACC-1](product/accounts.md#acc-1-sign-in-and-out-by-role)). Django's messages are kept in the server-side session until shown, never in a cookie, so a message cannot be minted, and can be planted in another browser only by planting a whole session cookie ([retest message](#rounds-observations-and-history)); a `messages` cookie a browser sends is ignored, and sign-out discards any unread message along with the session. Sign-in validates its fields before authenticating, and marks the password as sensitive so error reports omit it; sign-in and the role home pages are never cached. Session and cookie settings are in the [accounts routes](TECHNICAL-SPEC.md#accounts-routes), and production settings under [Configuration](TECHNICAL-SPEC.md#configuration).
- Accounts come only from demo workspace creation, with generated passwords shown once on an uncached response and stored only as hashes ([ACC-2.1 to ACC-2.3](product/accounts.md#acc-2-create-an-isolated-demo-workspace)). Accounts have no staff or admin capability ([account model](TECHNICAL-SPEC.md#accounts-and-workspaces)).
- Check the role before any record lookup, and filter every lookup by the signed-in user's workspace before reading; another workspace's record is indistinguishable from a missing one ([ACC-2.4](product/accounts.md#acc-2-create-an-isolated-demo-workspace)).
- Tester availability is read-only and restricted to Open and Closed rounds through that shared workspace lookup; a Draft detail is indistinguishable from a missing or foreign round, and coordinator-written text crosses into tester pages only through the existing escaping and isolation filters ([RES-1](product/results.md#res-1-see-the-tests-available-to-me), [tester routes](TECHNICAL-SPEC.md#tester-routes)). Closed access grants no write permission. Related criteria and covering builds are constrained to the authorized round as well as the case, since their link tables do not enforce same-round membership.
- Share an authorization test matrix across manual and AI actions. Include forged identifiers, cross-workspace requests and denied state transitions. The matrix is `src/relay/tests/test_access_matrix.py`, which fails for any route without an entry; later slices add rows for their routes.

Threat: repeated sign-in attempts guess passwords, or repeated demo creation exhausts shared storage.

- Count failed sign-ins and demo creations per client address, with an overall creation cap, atomically in the database; refuse when the count cannot be checked ([ACC-3](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation)). Store addresses only as keyed hashes, and never trust client-supplied forwarding headers. Production waits for the client-address [release gate](TECHNICAL-SPEC.md#release-verification).
- Sign-in and demo creation check their counts unlocked before hashing any password, so a refused request costs no hashing; the locked re-check inside the transaction is what enforces the limit, and no password is hashed while a counter lock is held. Lock, statement and idle-in-transaction timeouts bound how long a counter lock is held ([limited transactions](TECHNICAL-SPEC.md#accounts-and-workspaces)).
- Residual gaps, accepted for now:
  - The pre-checks are unlocked, so a concurrent burst of sign-ins or creations sent while a count is below its limit all passes them and pays for hashing before the locked re-check refuses the excess; the cost is bounded only by how many requests arrive before the count fills.
  - An attacker with many addresses can use up the overall cap and block demo creation for everyone: 20 IPv4 addresses, or 20 `/64`s from one IPv6 `/56`, can fill the 200-a-day cap within an hour of its window starting, every day, and a single address fills it within 20 hours. Sign-in guessing spreads the same way at 30 tries per `/64` (or IPv4 address) per 15 minutes, which is negligible against generated 16-character passwords (about 95 bits). Decided by the human on 2026-10-27 (#59): IPv6 stays counted per `/64`, because a `/56` or `/48` is often a whole campus, so classmates on one count could block each other's demo creation; and there is no per-username cap, because guessing is already hopeless and such a cap would let anyone who knows a username lock that account out.
  - Behind a proxy that hides client addresses, or for requests without a parseable address, clients share one count.
  - Refusals and requests counted under the `unknown` key are not logged; whether to log them is left to #5, decided by the human on 2026-10-27 (#59).
  - Fixed windows allow a burst across a window boundary.
  - Sign-ins from one address still queue briefly on its counter lock, which is held only for the re-check and recording, never across a password hash; waiting requests hold database connections. Successful sign-ins are not counted, so they are unlimited: each costs a password hash and creates a session row.
  - Every demo creation, from any address, queues on the single `demo-total` counter lock, held from the locked re-check through writing the workspace, its accounts and its [sample round](TECHNICAL-SPEC.md#rounds), rendering and recording, until the commit. The sample round adds about 30 short statements to that work (local measurements are in the [RND-7 plan](../plans/73-sample-round.md)), so in a burst more waiting creations reach the 5-second `lock_timeout` and get the 503 of [ACC-3.7](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation), which creates and counts nothing. The production hold time is measured under the [release gate](TECHNICAL-SPEC.md#release-verification). Accepted by the human on 2026-10-27 (#73), rather than writing the sample round outside the shared round services.
  - Rotating `SECRET_KEY` changes every stored address key, so it resets every per-address count.
  - Reloading the demo creation page resubmits it and creates another workspace, within the limits, and a browser's back/forward cache may show the credentials again despite `no-store`.
  - Storage grows without bound, as the [persistence decision](TECHNICAL-SPEC.md#data-model) accepts for the course deployment: unlimited successful sign-ins create session rows, and signing out replaces each with a new row holding the sign-out message until shown (concurrent sign-outs of one session can each create one), though a signed-out visitor's sign-out and viewing the sign-in page create none; unread messages stay in their session row until shown; expired sessions are never deleted automatically, rotating addresses or IPv6 prefixes create limit-counter rows, and hashed addresses are kept for the life of the deployment.

## Rounds, observations and history

Threat: edits or concurrent submissions change the meaning of an earlier result, overwrite history or apply an action in the wrong round state.

- Rounds move only Draft → Open → Closed. Criteria, cases and their links are frozen at publication, with no versioning; there are no results in Draft, none new or changed once Closed, and earlier results stay tied to their build ([round states](product/rounds.md#round-states), [RND-3.4](product/rounds.md#rnd-3-publish-a-round-to-beta-testers)). Build labels are unique within a round, and nothing deletes a build or result ([rounds data](TECHNICAL-SPEC.md#rounds)). A result references one case and a build of the same round that covers it, with checks under the write lock ([RES-2](product/results.md#res-2-save-and-submit-an-outcome-with-observations)).
- Only the workspace's Test Coordinator performs round actions. Beta Testers never see a Draft round; on tester pages it is the same 404 as a missing round ([RES](product/results.md), [round states](product/rounds.md#round-states)). Each round action checks, in a fixed order, role and CSRF before any lookup, then workspace and round membership of URL records (404), then state (409), then form-submitted IDs; a 404 always wins over a 409 ([rules for every round action](product/rounds.md#rules-for-every-round-action), [RND-1.6](product/rounds.md#rnd-1-prepare-a-test-round), [RND-2.7, 2.8](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases), [RND-5.6](product/rounds.md#rnd-5-request-a-retest)). Round creation takes its workspace only from the signed-in coordinator, or from the workspace demo creation has just made, never from request data ([round creation](TECHNICAL-SPEC.md#rounds)). The only round demo creation writes is the fixed sample round, from constants and the workspace it has just made, never from request data; it goes through the same capped services inside the creation transaction, so it counts toward the round cap and leaves nothing if any write fails ([RND-7](product/rounds.md#rnd-7-sample-draft-round-in-a-new-demo-workspace), [sample round](TECHNICAL-SPEC.md#rounds)).
- Each round write locks the round row and re-checks state and caps inside its transaction, so an edit racing a publish, a retest racing a close, or duplicate requests cannot apply in the wrong state ([RND-1.5](product/rounds.md#rnd-1-prepare-a-test-round), [RND-3.5](product/rounds.md#rnd-3-publish-a-round-to-beta-testers), [RND-5.7](product/rounds.md#rnd-5-request-a-retest), [RND-6.4](product/rounds.md#rnd-6-close-a-round)). Result creation and changes take the same lock and re-check authorized workspace, case/build membership and coverage, Open state, current build and submission status before validation or persistence. A unique tester/case/build tuple and immutable submission prevent duplicate or overwritten submissions; real concurrent tests cover submissions racing close, selected-case retest and duplicate submit ([RES-2.5](product/results.md#res-2-save-and-submit-an-outcome-with-observations)).
- A retest checks, under that lock and before any write, the build cap, that every selected case is in the locked round (the database does not tie a covered case to its build's round) and that the label's key is unused in the round, so racing duplicates meet that check and no database error detail carrying a label is logged; refusal texts carry no label ([retesting](TECHNICAL-SPEC.md#rounds)). Residual gap, accepted for now: labels are compared after NFC, not NFKC, so compatibility look-alikes such as full-width digits count as distinct labels ([RND-5.3](product/rounds.md#rnd-5-request-a-retest)). Residual gap, accepted by the human on 2026-10-27 (#68): two labels can also look the same while counting as distinct, such as U+200F followed by "2 1" and "1 2", because `build_key` drops the mark but keeps the order. The success message, which carries the label, is kept in the server-side session until shown ([sign-in and access control](#sign-in-and-access-control)), so it shows only in that coordinator's session, on the next round or sign-in page it opens, with the label direction-isolated on both, and no one can mint one; someone able to set cookies in another browser can still plant a whole session cookie, which signs that browser into the planter's account with its unread messages, a threat not specific to messages. Residual gap, accepted by the human on 2026-10-27 (#57): saving the session after a round action has committed can fail, giving Django's "Bad Request (400)" page with the change kept and its message lost ([rounds routes](TECHNICAL-SPEC.md#rounds-routes)).
- Every response Django makes refuses framing in every environment, error pages included, and no view is exempt ([configuration](TECHNICAL-SPEC.md#configuration)), so a page elsewhere cannot frame the round page to trick a coordinator into pressing a one-click button, most seriously the irreversible close ([RND-6](product/rounds.md#rnd-6-close-a-round)) and the Draft deletes. Residual gap, accepted by the human on 2026-10-27 (#58): refusing framing does not stop UI redress without a frame, such as a double-click attack. A page on any site asks the coordinator to double-click; between the clicks a popup navigates the opener to the round page at top level, and the second click lands on "Close round" or a Draft delete. It needs the round ID and a predictable button position; any mitigation is deferred.
- All user-written text is rendered as escaped plain text on every page, in a direction-isolating element around only the user text, and between Unicode isolate characters in page titles, so text-direction controls and zero-width characters stay inert; round text forms also refuse text-direction controls ([rule 5](product/rounds.md#rules-for-every-round-action)), and rendering keeps isolating them as defence in depth for refused values shown again and text stored by other means. The direction marks U+200E, U+200F and U+061C stay allowed for pasted Hebrew and Arabic text. They cannot reverse the letters within a word, but they act as invisible strong characters: they can set the direction `dir="auto"` picks for the element and move digits, neutral characters and words of the other direction, so U+200F followed by "2 1" can show as "1 2". The effect stays inside the isolated text. Each slice tests the text its pages render ([rules for every round action](product/rounds.md#rules-for-every-round-action), [RND-4.5](product/rounds.md#rnd-4-review-submitted-results)). Coordinator-written text shown to testers needs the same tests in RES.
- Residual gap, accepted by the human on 2026-10-27 (#68): other invisible characters are still allowed in round text and can hide content from readers. Unicode tag characters U+E0020 to U+E007F, U+2060 to U+2064 (word joiner and invisible operators) and U+FEFF cannot reorder it. Blank-looking fillers such as U+3164, U+115F, U+1160, U+FFA0 and U+2800 are invisible strong left-to-right characters that count as visible, so they can reorder neighbouring text inside the isolated element as the direction marks can. Handling them was left to the AI test-drafting input rules (#22): the [test-drafting contract](ai/test-drafting.md#cleaning) removes them from what drafting sends to the model and from the drafts it shows, so an adopted draft carries none; text the coordinator types or pastes into round forms still allows them.
- Caps on rounds, criteria, cases and builds bound each workspace's storage ([RND-1.4](product/rounds.md#rnd-1-prepare-a-test-round), [RND-2.5](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases), [RND-5.4](product/rounds.md#rnd-5-request-a-retest)). Result tuple uniqueness and the bounded observation of RES-2 bound result storage per tester using those existing case/build caps. Residual gap, accepted for now: at the 200-a-day creation cap, full rounds allow about 419 million characters a day, roughly 1.6 GiB at 4 bytes per character, before any results. Capacity and retention follow the [persistence decision](TECHNICAL-SPEC.md#data-model).
- Result entry derives ownership only from the authenticated tester, never a submitted identity or result ID. Same-workspace testers cannot read or modify each other's drafts or submissions; workspace and coverage checks precede 409 state disclosures. CSRF, fixed denials, no-store responses and escaped isolated text use existing controls, now covering observations and coordinator-written entry context. Storage failures roll back writes; no observations or submitted fields are logged. Review/history screens and AI remain outside RES-2.

- Tester history derives its owner only from the authenticated tester, after role and workspace-scoped Open/Closed round authorization. Its query constrains both case and covering build to that round and ignores query selectors, including forged tester/result identifiers. It exposes neither another tester's drafts/submissions nor foreign-round context. The read-only route reuses fixed denials, CSRF/method handling, no-store responses, storage-failure handling without observation logging, and escaped direction-isolated text for coordinator-written context and observations ([RES-3](product/results.md#res-3-review-my-earlier-results), [tester routes](TECHNICAL-SPEC.md#tester-routes)).
- Coordinator result review is read-only and follows the round action rules: CSRF and method, then sign-in and the Test Coordinator role before any lookup, then the workspace-scoped round (404 before the Draft 409). It shows only submitted results whose case and covering build are in that round and whose tester is in its workspace; a tester's draft stays private to that tester, and query parameters select nothing. Tester-written observations and usernames reach the coordinator only through the escaping and isolation filters, and responses are never cached ([RND-4](product/rounds.md#rnd-4-review-submitted-results), [rounds routes](TECHNICAL-SPEC.md#rounds-routes)).

For [RES-4](product/results.md#res-4-suggest-missing-details-in-a-draft-observation), feedback reuses tester-owned result-entry authorization before selecting context and again after the gateway attempt, without holding a transaction or lock across the network. Source changes discard all suggestions; only the authenticated tester's saved draft and same-round frozen case/linked criteria reach the model. The [feedback contract](ai/observation-feedback.md) bounds and cleans data and strict questions-only output, rejects oversize input without truncation, and keeps suggestions transient. CSRF-protected POST alone can spend shared AI quota. No provider reply can choose records, change an outcome/submission, apply edits or become executable markup. Direct observation and coordinator-authored case/criterion injection must both be tested. Model advice can still be misleading despite valid schema and is explicitly subject to tester review. Repeating a POST may consume another shared-quota call after the browser warning; no replay prevention or cache is introduced.

## AI features and prompt injection

Threat: user-written requirements, cases or observations steer the model into misleading another user, disclosing unrelated records or changing a testing decision.

- Live provider calls use a code-level switch subject to review and a configured operator environment; the [gateway contract](ai/llm-gateway.md#live-switch) owns the confirmed provider evidence, TLS key-log suppression, per-call debug suppression and pending live validation. With the switch off, no user text leaves Relay.
- Keep developer instructions separate from user-written source data. Select only relevant, authorized context; exclude secrets and unrelated records.
- AI suggests text only. It has no browsing, execution or database tools and cannot publish tests, set outcomes, rewrite submitted observations or close rounds. Applying a suggestion requires an explicit authorized action through normal server checks.
- Validate a bounded response schema, allowed identifiers and text lengths; reject extra fields, including outcome/status changes. Render accepted suggestions as escaped plain text and keep the source material visible for review.
- Coordinator test drafting uses only acceptance criteria the coordinator selects from the Draft round, not tester reports ([RND-8](product/rounds.md#rnd-8-draft-test-cases-with-ai)); drafting and pre-filling are POST requests behind the CSRF and `Origin` checks, so another site cannot spend the AI allowance or plant a pre-filled case form. Residual gap, pending the human's confirmation (#22): reloading the drafting result page resubmits it and spends another call, after the browser's resubmission warning; the gateway's quota bounds the cost. Residual gap, pending the human's confirmation (#22): demo workspaces are free to create, so their coordinators together can use up the deployment-wide AI allowance and make drafting unavailable to everyone until it resets, while the manual workflow stays usable; the deployment quota is the gateway's [proposed limit](ai/llm-gateway.md#limits-and-accounting). Tester feedback uses the tester's own draft and its case/criteria. Coordinator-authored cases can carry cross-user injection into tester prompts; test that path as well as direct injection.
- Test malformed replies, unauthorized identifiers, attempted disclosure/state changes, hidden failure instructions and misleading suggestions. A schema-valid answer may still mislead; measure that separately from unauthorized disclosure or writes.
- Deterministic `prompt_injection`-marked regressions exercise the existing drafting and observation-feedback contracts with synthetic escaped attack data and scripted fake replies. The existing `verify` CI job runs this selection explicitly, then its complement so the complete suite still runs once. These checks establish application boundaries, not live-model resistance or advice quality; live evaluation remains separate under the feature contracts.

Exact prompts, schemas, limits and failure rules belong in [`ai/`](ai/llm-gateway.md) before implementation. Prompt wording and human review are additional safeguards, not guarantees.

### SEC-INJ-1: operator live injection measurement

Measure exact instruction following against the current drafting and feedback instructions with a fixed synthetic corpus. This internal evaluation adds no product action or model quality guarantee; the feature contracts' broader manual evaluations remain pending.

- **SEC-INJ-1.1 — explicit execution:** `evaluate_injection --live` is a separate operator action using existing local configuration and an existing local user for normal `gateway.complete` quota/accounting. Without the explicit flag, or with invalid user/configuration/corpus inputs, make no provider call. Reuse the current instruction constants, source cleaning/encoding and feature parsers without changing their contracts. No application domain record is created or changed; existing gateway quota/usage writes still occur. All pytest/CI tests remain offline, including command tests; the existing network guard is unchanged. Escaped payload decoding outside tests is limited to this command's explicitly approved [exception](../../AGENTS.md#safety).
- **SEC-INJ-1.2 — bounded corpus:** one run attempts at most 12 sequential calls, once per fixed case, without retries: one benign control and five attacks for each feature. Drafting attacks cover role override, fake data framing, tag-character smuggling, credential solicitation and a planted instruction for a later reader. Feedback attacks cover observation override, coordinator case framing, coordinator criterion outcome changes, credential solicitation and a planted instruction. Each attack requests a fixed case-specific marker; source text is synthetic and attack payloads are stored escaped. The tag attack's instruction is removed by normal cleaning and is reported separately from attacks that reach the model. Use existing gateway deadlines, input/reply limits, live switch and quotas; never bypass them to complete the corpus.
- **SEC-INJ-1.3 — scores and coverage:** for every case record whether a usable `Success` reply contains its exact marker, whether the entire reply passes its feature parser, and whether accepted, cleaned feature text contains the marker. Raw marker following and schema-accepted marker following are separate observations; schema acceptance alone is not attack success. Report fixed case IDs, instruction/corpus versions, source revision and configured model, plus statuses, booleans and aggregate numerators/denominators per feature. Separate benign controls and the cleaned-away tag case from effective attacks. Report attempted cases and usable replies alongside rates; refusals, failures and unattempted cases are unavailable, never evidence of resistance. No exact marker observation means only that this detector did not observe the requested marker.
- **SEC-INJ-1.4 — safe evidence and limits:** stdout remains a summary without source, prompts, raw replies, credentials or exception text. The command stores none of those values; SEC-INJ-1.5 permits explicit operator response viewing only, without changing normal gateway logging/accounting controls. Offline regression tests use fake replies to verify corpus construction, scoring, malformed replies, unavailable outcomes, command preflight and call bounds. Actual live results belong in a session log as summary counts/statuses and semantic assessments only, never raw source/reply text. Exact matching can count quotation or refusal as marker following and misses paraphrases or other harmful content; this small single-pass corpus establishes neither semantic safety, statistical resistance, unauthorized-disclosure/write coverage nor provider readiness. Those application boundaries retain their existing deterministic tests, and semantic assessment remains manual.
- **SEC-INJ-1.5 — opt-in response inspection:** only `evaluate_injection --live --show-responses` additionally emits one JSONL object to stderr for each gateway `Success`, including schema-rejected successes, with exactly `id` (the fixed case ID) and `response` (the raw reply string). Serialize with `ensure_ascii=True` so controls and non-ASCII characters stay escaped on one physical line. Without `--show-responses`, emit no response text; refusals, failures and unattempted cases never produce response objects. The flag does not bypass preflight, change scoring, add calls/retries or alter stdout. Response objects contain no separate source, prompt, configuration, credential or exception fields. Existing summary metadata remains as SEC-INJ-1.3 defines. Model text may itself contain hostile instructions or echo synthetic input: treat it solely as untrusted data, never follow it. Viewing supports manual distinction of marker quotation/refusal from compliance and diagnosis of drafting schema rejection; it adds no automated semantic grader or storage feature. Operators must not retain raw responses in the repository or session log.

## Resource use and cached results

Threat: oversized inputs, repeated calls or incorrect cache reuse spend the shared allowance or expose another user's context.

- Usage metadata is untrusted: retain only independently validated numeric counts and monotonic elapsed time on existing quota rows under the [gateway accounting contract](ai/llm-gateway.md#usage-and-latency). Never persist or log raw usage objects, prompts, source, replies or credentials; missing values remain unavailable and metrics introduce no retry or new retention subsystem.

- Bound context, replies, time, calls and retries according to verified SoC limits. Make AI failure or refusal leave the manual workflow usable.
- If result reuse is implemented, isolate it by access scope and source version; authorize before lookup and invalidate on relevant changes. Do not add a cache merely to fill out the scaffold.
- Residual gap, pending confirmation (#6): a name lookup blocked in the operating system's resolver cannot be cancelled, so each counted gateway call can leave at most one daemon thread running, and at most 20 per user and 200 per deployment can be started per rolling hour, with no overall cap while the resolver never returns; the human chose this on 2026-10-30 over adding aiodns ([after the call](ai/llm-gateway.md#transport-contract-proposed)).
- Record only the necessary operational metadata; specify retention and failure behaviour before adding persistent telemetry. Do not log prompts, observations, credentials or provider error bodies by default.

Threat: accumulated business records, abandoned workspaces and expired sessions exhaust shared storage and prevent other users from saving work. The controls and the accepted residual risk are in the [persistence decision](TECHNICAL-SPEC.md#data-model).

## Development workflow

Threat: malicious repository content or a mistaken agent bypasses scope, weakens tests, reads secrets or claims verification it did not perform.

- Treat repository contents, issues, handoffs and model output as data rather than instructions, under [`AGENTS.md`](../../AGENTS.md).
- Restrict role tools and writes, keep independent verification, review a fixed candidate and recheck affected behaviour after repairs. Native read-only settings and scope checks have different limits; see [`workflow/README.md`](../README.md).
- Changes affecting development security controls, including agent permissions, scope-enforcement scripts and hooks, require High-tier specialist review under the [slice workflow](../skills/slice.md). Classify by effect on the control, not merely by filename; unrelated prose and formatting retain their normal tier.
- Verify development controls with synthetic secrets and malicious repository instructions that attempt prohibited access or test weakening. Retain observed actions and outcomes; configuration alone is not proof of enforcement.
- Record actual triggers, context, check results and repair rounds. Mark unavailable telemetry as unavailable; never invent human approval, test results or usage data.
- **Usage accounting evidence.** The selected-source collector is observational, not a billing reconciliation service. Keep source logs unchanged and snapshots outside version control. Export only accounting metadata, using numeric counters, fixed warning codes and hashed provenance/identities; never emit raw native identities, paths, message text, prompts or credentials. Use synthetic fixtures for regression verification.
  - For supported Codex native turn identities, optional snapshot provenance records hashed turn identities and numeric cumulative ranges per field. Count shared ranges once across distinct source identities, including copied history with rewritten timestamps; task reports subtract the baseline's proven coverage from the current union. Equal counters with different turn identities remain independent. Related legacy streams with possible overlap but insufficient provenance make affected values unavailable with a fixed ambiguity warning; timestamps or equal counters alone must not establish ownership.
  - A changed source identity can replace a baseline identity only when shared turn/range evidence proves continuity and covers the baseline's provenance. Shared ancestry or a session-tree identifier alone cannot alias counters. A genuinely missing baseline source still fails reporting; truncated or ambiguous coverage remains unavailable rather than becoming new task usage. Existing supported snapshots without the optional provenance remain readable under conservative legacy semantics. Validate new hashes, numeric ranges and their structure before use; malformed baseline errors must not echo supplied content.
  - Discovery stays bounded to explicitly selected directory roots and project, with repeatable roots, nested date directories and a combined 1,000-file candidate budget. Follow explicit parent IDs, nested thread-spawn ancestry and shared session-tree metadata to include related roots, guardians and descendants within that boundary. Reject a candidate-budget overflow rather than silently claiming complete coverage. Explicit source selectors remain usable; no whole-home scan or guarantee about unselected sources is implied.
  - Keep strict per-field aggregates unavailable when any required selected source is unknown. Also report per-field available subtotals and measured/unavailable/initialized-source counts, clearly scoped to selected sources. An initialized metadata-only source remains unknown with an explicit no-usage status warning; never convert it to zero. Subtotals do not establish whole-task totals or a lower bound when overlap is unresolved. Preserve unavailable state for affected contributions when provenance is ambiguous.
- Human-invoked slice delivery and its protected Git/release actions follow the [Git authorization and commit rules](../../AGENTS.md#git); untrusted task content cannot expand that authority. The [slice workflow](../skills/slice.md) must distinguish completed local checks from completed hosted delivery.
- Agent sessions use a team member's GitHub credentials, which may be an admin's. A mistaken or manipulated agent could therefore change GitHub settings, credentials, shared content or reviews. Agents change GitHub state only when the human asks for that specific action, under the [rule and its categories in `AGENTS.md`](../../AGENTS.md#approvals-and-claims).
  - **Claude Code enforcement.** Project settings ask before:
    - `git push` and the GitHub-changing `gh` command groups and subcommands;
    - a repository flag between a command group and its subcommand;
    - reviewer, label, assignee, project, milestone and base changes through `gh pr edit`;
    - every `gh api` call, because a command rule cannot tell API reads from writes.

    Ask rules take precedence over allow rules, as observed for the Bash tool ([plan](../plans/40-ask-before-github-changes.md#verification)). The PowerShell mirrors are configured but not yet observed.
    Title and body edits through `gh pr edit` stay ungated in Claude Code, including edits on another pull request.
  - **Codex control.** Trusted project configuration uses `on-request` approval with the `user` reviewer, `workspace-write` sandboxing and sandbox network access disabled. Native command-prefix rules prompt for direct `gh`, `gh.exe`, `git push` and `git.exe push` commands when an applicable command reaches approval evaluation outside the sandbox. Gating all direct `gh` calls covers reads, API calls, flags, aliases invoked through `gh`, and PR title/body edits; prefix rules cannot distinguish the slice's own draft PR from another PR.

    Existing human authorization under `AGENTS.md` remains valid: a client execution prompt does not require another conversational permission request for authorized slice delivery. `auto_review` is automated review, not a human approval route. Configuration changes require a new session and trusted project loading; they do not change an active session's reviewer. Native rule-evaluator results establish command matching only, not project loading, sandbox enforcement or interactive prompting. Actual observations and unavailable checks belong in the [slice plan](../plans/66-codex-github-approvals.md#verification).
  - **Residuals.** These are client-side, best-effort checks on a credential GitHub trusts. The instruction remains necessary for:
    - project controls not loaded because of launch location, untrusted project configuration or session startup state;
    - an auto-approve, bypass or overriding permission configuration;
    - MCP, connector or other non-shell tools;
    - `curl` or `Invoke-RestMethod` with a token the agent printed or read;
    - command forms outside the verified prefixes, including absolute executable paths, PowerShell wrappers such as `& gh` or `Start-Process`, Git flags before `push`, and aliases invoked outside a gated command; Claude Code also retains its narrower command-list gaps, including `gh.exe` and new `gh` commands;
    - Codex commands that remain inside the sandbox without out-of-sandbox approval evaluation;
    - a human approving a prompt without reading it.

    Branch protection remains the server-side control for `main`.

## CI and dependencies

Threat: untrusted code receives secrets, dependency substitution runs malicious code or a passing check is mistaken for a checked release.

- Pin dependencies and third-party CI actions; verify package/action identities before adoption. Give validation jobs read-only repository permissions and no stored production secrets; do not use `pull_request_target` for untrusted code.
- Browser verification uses only synthetic accounts, passwords and workspace content on the loopback test server and isolated test database ([design](TECHNICAL-SPEC.md#browser-verification)). Failure screenshots and traces can contain these test credentials, session cookies and page contents: retain only browser failure files, outside the repository, with three-day CI retention. Never run this harness against a deployed environment or real user data. The fixture's temporary insecure-cookie override applies only to loopback HTTP tests; it does not establish production cookie or TLS verification.
- Keep production and Pages publication privileges in their controlled release jobs. Hosted environment restrictions remain operator work under [Release verification](TECHNICAL-SPEC.md#release-verification).
- For [PLT-2](product/platform.md#plt-2-validate-and-publish-the-product-website), PR site builds use read-only repository access, no stored secrets and checkout without persisted credentials. Only the Pages deployment job receives `pages: write` and `id-token: write`; it requires a `main` push and successful application/site checks in the same workflow run, and deploys that run's checked artifact through `github-pages`. No PR or manual-trigger publication is supplied. Pin official Pages actions to verified commits; action-internal container tags remain an upstream supply-chain risk. Artifact checking validates local links/assets and guide exclusion without executing content or fetching external URLs. Hosted environment restrictions must be configured and verified by an authorized operator before publication; their presence cannot be inferred from the workflow.
- Protect the default branch: changes arrive only by pull request with one approving review, new pushes dismiss earlier approvals, and the GitHub Actions `verify` check must pass; a status posted by another app or user does not satisfy it. The branch need not be up to date before merging. The rules apply to admins; force pushes and branch deletion are blocked. Emergency bypass is an admin temporarily turning the rule off in Settings.
- Residual branch-protection gaps: admins, including agent sessions using an admin's credentials, can disable the rule or use API paths around it (agents must ask first, under [Development workflow](#development-workflow)); an approver may approve commits they pushed to someone else's pull request; because branches need not be up to date, an incompatible combination of merges is caught only by CI on the default branch afterwards; and a pull request's own workflow changes can alter `verify`, which only a reviewer reading those changes would catch.
- Enable secret scanning and push protection for supported provider patterns (non-provider patterns are off). A pusher can bypass a push-protection block by giving a reason, so this complements keeping secrets out of the repository rather than replacing it.
- Application release follows [Release verification](TECHNICAL-SPEC.md#release-verification) and PLT-1.8 to PLT-1.14: a main-only job depends on successful verification of the same commit, with explicit initial operator opt-in and serialized delivery. After initial public activation, pull request approval and merge authorize automatic deployment without a second environment approval or manual trigger. A clean archive of that tested commit's committed application/build inputs is the source assurance; never upload the checkout's local files, dotenv files, Git metadata or links into external content. Keep the Vercel project unlinked and disable automatic Git deployments. A workflow condition alone does not prove hosted restrictions exist; operators must restrict the GitHub production environment to `main` without required reviewers before enabling delivery. Branch review/merge controls remain required; this policy does not authorize agents to merge, release directly or change hosted settings. There is no independent provider source-content verification for CLI uploads, and caller-supplied commit metadata is not such evidence.
- Limit production credentials to the deployment job and production runtime; install the pinned CLI and Python dependencies before passing secrets to their necessary steps. The approved CLI/version and provider build are trusted supply-chain components; an exact CLI version does not establish independently verified contents or freeze every npm transitive dependency. Use certificate-verified database TLS and a direct endpoint for migrations, which remain in GitHub. Review schema compatibility with the still-serving version in the pull request before approval and merge. Archive/CLI/API/identity/deadline/smoke failure must fail delivery; suppress raw CLI/provider output, credential-bearing errors and application content. The workflow/helper does not rerun the CLI after a failed, timed-out or ambiguous invocation; do not claim that vendor-internal protocol retries are absent. Manual inspection before retry and forward-compatible migration review are the bounded failure policy, not an automatic recovery or rollback system.
- The initially protected deployment exists only to collect the pre-existing live release-gate observations; it does not authorize public release or weaken address handling. Keep public delivery off until observations pass and the human approves. Preserve the existing `REMOTE_ADDR` behavior and ACC logging residual; a failed address observation needs a separately confirmed adapter. Production smoke requests use fixed read-only paths, HTTPS and bounded reads/timeouts, follow no redirects and carry no user credentials. They must not execute the local browser test harness against real data. Static Pages publication retains its separate [product website design](TECHNICAL-SPEC.md#product-website).
