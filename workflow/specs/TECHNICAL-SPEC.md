# Technical spec

How Relay will be built and run. What it will do is in [`PRODUCT-SPEC.md`](PRODUCT-SPEC.md). The application runs locally and in CI only. Workspaces, accounts and sessions (ACC-1), demo workspace creation (ACC-2), abuse-limit counters (ACC-3), test rounds with their title and state (RND-1), their acceptance criteria, test cases and links (RND-2), builds with publishing (RND-3), retests as further builds (RND-5), and closing with its closing time (RND-6) exist; other business schema and hosted environments remain planned.

## Architecture

- One Django project that renders HTML on the server, with no separate front end. Application code and its tests will live under `src/`.
- PostgreSQL for application storage and database-backed tests.
- Configuration from environment variables, with no committed credentials.
- SoC LLM through one shared gateway; feature code selects authorized context before invoking it. The planned boundary is in [`ai/llm-gateway.md`](ai/llm-gateway.md).

`src/manage.py` starts the `relay` Django project; `relay.wsgi` is its WSGI entry point and `relay.pages` owns public presentation. Shared templates live in `src/relay/templates/`. The `accounts` app (`src/accounts/`) owns the [workspace and account models](#accounts-and-workspaces) and the accounts routes, with Django's `auth`, `contenttypes`, `sessions` and `messages` apps; `django.contrib.admin` is never installed. The `rounds` app (`src/rounds/`), added by RND-1, owns the [round models](#rounds) and the [rounds routes](#rounds-routes). ACC-1 adds the accounts apps; until then no auth/session apps or business models are installed. Runtime and dependency pins belong in the root configuration files.

## Data model

Only the subsections below are specified. Design workspaces, role-based accounts, rounds, requirements, cases, build references and results around the [product areas](PRODUCT-SPEC.md#areas). Before schema implementation, settle ownership, state transitions, published-case edits, submitted-observation edits and result-history/version rules. Do not infer these from a proposed screen or table name.

Persistence and retention, decided for ACC-1 (see its [plan](../plans/2-sign-in-by-role.md)):

- Workspaces, accounts, rounds, results, limit rows and their hashed address keys are kept for the life of the course deployment. Nothing expires or is deleted automatically, and there is no cleanup subsystem.
- An expired session is refused by its absolute expiry; its row is not deleted automatically. Signing out a signed-in user deletes their session row, then the sign-out message starts a new anonymous session row, which expires after 8 hours, is emptied once the message is shown, and is replaced at the browser's next sign-in. A signed-out visitor's sign-out, and viewing the sign-in page, create no row.
- When shared storage is exhausted, a failed write is not retried, and the user gets that route's existing error page: the generic 500 of [PLT-1.3](product/platform.md#plt-1-django-foundation-and-continuous-verification), or the 503 page that [ACC-2.5](product/accounts.md#acc-2-create-an-isolated-demo-workspace) and [ACC-3.7](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation) define. Saving the session at the end of a request is the exception: a failed save of an existing session row gives Django's "Bad Request (400)", and a failed creation of a new one, as at sign-out, the generic 500 ([rounds routes](#rounds-routes)). A route that writes in a transaction rolls the whole transaction back. Existing records, including result history, are never deleted or overwritten to make room.
- Before peer testing, an operator checks the hosting database's storage use. Exhaustion and unbounded session and counter growth are [accepted residual risks](SECURITY-SPEC.md#sign-in-and-access-control) for the course deployment.

### Accounts and workspaces

For [ACC](product/accounts.md). Retention follows the [persistence decision](#data-model) above.

- **Workspace:** a unique name, `Demo workspace <suffix>`, and its creation time. Every workspace-owned record has a non-null workspace reference. Routes check the role first, then look records up through one shared helper that filters by the signed-in user's workspace before reading and gives the 404 of [ACC-2.4](product/accounts.md#acc-2-create-an-isolated-demo-workspace) for any other workspace's record.
- **Workspace lookup helper:** `accounts.workspaces.workspace_records(user, model)` returns `model`'s records whose `workspace` is the user's workspace. A route reads a URL-named record with `get_object_or_404` on that queryset, so another workspace's record raises the same `Http404` as a missing one; a form uses that queryset for its choice field, so another workspace's ID gets the field's invalid-choice message. Every 404, including unresolved paths, renders `404.html` with "Page not found." From RND-1 the rounds views and the Coordinator home's round list use the helper.
- **Account:** a custom Django user model (`accounts.User`, the `AUTH_USER_MODEL`), added by ACC-1 before any persistent database (in particular production, under #5) is migrated. It has a globally unique username, a Django password hash, a non-null workspace (`PROTECT`) and a role of `coordinator` or `tester`, all fixed at creation, plus Django's last-sign-in time. The model has no staff, superuser or permission fields, and `django.contrib.admin` is not installed, so there is no admin route.
- **Generated credentials:** usernames are `coord-<suffix>`, `tester1-<suffix>` and `tester2-<suffix>`, sharing the workspace's suffix of 8 random lowercase letters and digits. A new suffix is drawn while the workspace name or any of the three usernames already exists, up to 3 draws; if the last one also exists, or a concurrent creation takes it first, the unique constraint fails and ACC-2.5 applies. Each password is 16 random characters from `a-z`, `A-Z` and `0-9`, generated with `secrets` and hashed before any lock is taken. Plain passwords exist only in memory while rendering the creation response.
- **Creation:** one transaction holds the limit counts, the workspace, its accounts, its sample round and the rendering of the creation response, so any failure rolls everything back ([ACC-2.5](product/accounts.md#acc-2-create-an-isolated-demo-workspace)). The `/demo/` view first reads both creation counts without locking them and, if either has reached its limit, gives the 429 of [ACC-3.4](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation) before generating anything, so a refused request costs no password hashing. Otherwise it generates and hashes the passwords, then opens one `transaction.atomic()` block. Inside it, the view calls `limits.start()`, locks both counts and checks them again, giving the same 429 if either has been reached meanwhile; one function, `accounts.demo.create_demo_workspace`, writes the workspace and its accounts in a savepoint, so it is also all-or-nothing on its own (RND-7 adds the sample round there); and the view renders the page to a string. The view then records the creation in both counts. The response is built from that string only after the block commits, with `Cache-Control: no-store`. Either 429 is returned as a normal response, never raised through the block's exception handler. Any other exception in the block, from storage, the commit or rendering, rolls back and gives the 503 page (`503.html`, status 503); the view logs the exception with its traceback only, never the passwords or the rendered page. A constraint violation's message may name an existing username or workspace name, never a plain password. Plain passwords are Django sensitive variables in the creating functions, and a credential's repr hides its password, so error reports with frame variables do not show them either.
- **Limit counter:** `accounts.LimitCounter`, one row per scope and key, holding a window start and a count, unique on scope and key. The scopes are `sign-in` (per address: 30 per 15 minutes), `demo` (per address: 10 per hour) and `demo-total` (one row, key `all`: 200 per 24 hours), as in [ACC-3](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation). A migration creates the `demo-total` row. A count has reached its limit while it is at least the limit and the current time is before its window start plus its window; at or after that time it counts as 0. Recording a counted request sets the window start to now and the count to 1 if the count is 0 or the window has ended, and otherwise adds 1. Refused requests change no count or window start (ACC-3.3). The current time is `django.utils.timezone.now()`, so tests control it with `unittest.mock`.
- **Limit service:** `accounts.limits` defines the three limits and these functions, the only ones the views call:
  - `client_key(request)` returns the stored key of the client address (below).
  - `peek(limit, key)` reads a count without locking, for the sign-in and `/demo/` pre-checks; a missing row counts as 0.
  - `start()` sets, for the current transaction only (`set_config(..., true)`), `lock_timeout` to 5 seconds, `statement_timeout` to 10 seconds and `idle_in_transaction_session_timeout` to 10 seconds. Each limited transaction calls it first.
  - `lock(limit, key)` inserts the row with count 0, or else locks the existing row unchanged, in one `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` statement, and returns the locked row.
  - `reached(counter, limit)` and `record(counter, limit)` apply the rules above.
- **Limited transactions:** a creation locks its `demo` row, then the `demo-total` row. A sign-in POST first reads its `sign-in` count unlocked and, if the limit has been reached, refuses without validating the form or checking the password. Otherwise it validates the form and authenticates outside any transaction or lock, then opens one `transaction.atomic()` block that calls `start()`, locks its `sign-in` row, checks it again (refusing even a correct password if the limit was reached meanwhile) and records any failure, so concurrent attempts cannot overshoot and a rollback records nothing. No password is hashed while any counter lock is held. The session is started only after the block commits, so a failure in the block signs no one in. PostgreSQL counts the session as idle while Python works, so the idle timeout is longer than the work done while a lock is held: the re-check and recording during sign-in, and writing and rendering during demo creation, whose passwords are hashed first. PostgreSQL 17's `transaction_timeout` is not used: the statement and idle timeouts already guarantee that a lock is released. In `/demo/`, any exception from the pre-check through the creation block, password hashing included, gives the 503, as in [Creation](#accounts-and-workspaces); in sign-in, any `django.db.Error` from the pre-check through its transaction, authentication included, does. Either case covers a lock, statement or idle timeout and a failed commit, rolls back, and gives the 503 of [ACC-3.7](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation), logged with its traceback only. The timeouts must stay below the platform's function time limit, which is verified under the [release gate](#release-verification).
- **Client address:** `REMOTE_ADDR`, never a client-supplied forwarding header. IPv4 addresses count individually, an IPv4-mapped IPv6 address as its IPv4 address, and other IPv6 addresses by their `/64` prefix; a missing or unparseable address uses the fixed value `unknown`. The stored key is the hex SHA-256 `salted_hmac` of that value (the address, the prefix or `unknown`) with its own salt, never the address itself. Production depends on the client-address gate under [Release verification](#release-verification); a trusted-proxy header setting is a separate decision, needed only if that verification shows it.
- **Sessions:** Django's database-backed sessions. Sign-in sets an absolute expiry time 8 hours ahead, so later session writes cannot extend it ([ACC-1.6](product/accounts.md#acc-1-sign-in-and-out-by-role)); signing out a signed-in user deletes the session row, and the sign-out message then lives in a new anonymous session. Expired rows are not deleted automatically ([persistence decision](#data-model)).

### Rounds

For [RND](product/rounds.md). Field limits, caps and messages are in its criteria. Nothing here deletes a round, build or result; retention and full storage follow the [persistence decision](#data-model). A round belongs to one workspace and every other record below to one round. URL records are looked up through the workspace helper, then checked to be in the round the URL names; form-submitted IDs are checked against the round in the form's validation ([checking order](product/rounds.md#rules-for-every-round-action)).

- **Round:** a non-null workspace, a title of at most 120 characters, a state of `draft`, `open` or `closed` (a database check constraint), and its creation time; RND-3 adds its publication time (`published_at`, empty while Draft, set when publishing) and RND-6 its closing time (`closed_at`, empty until closing, set when closing). Lists order rounds by creation time, newest first, then by descending ID.
- **Round creation:** one function, `rounds.services.create_round(workspace, title)`, used by the new-round route and later by the [demo creation](#accounts-and-workspaces) transaction (RND-7). Its workspace argument is only ever `request.user.workspace` or the workspace ACC-2 has just created, never a value from request data. In a transaction, it locks the workspace row, counts the workspace's rounds, and creates a Draft round below the cap of 20 or raises an error the view shows as the [RND-1.4](product/rounds.md#rnd-1-prepare-a-test-round) message.
- **Text fields:** the form trims surrounding whitespace with Python's `str.strip()`, then counts characters (code points). A character is visible unless `str.isspace()` is true for it or its Unicode category is Cc or Cf; text without a visible character is treated as empty. A form field shared by all round text fields applies this check, the length limits and Django's null-character validator. Before trimming, it replaces each CR LF pair with LF, so a line break typed in a browser counts as one character. Criterion text, steps and expected result use a `<textarea>`; every round text input carries `dir="auto"`.
- **Acceptance criterion** (`rounds.Criterion`) and **test case** (`rounds.Case`): a non-null round and their text fields ([RND-2.4](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases)), with those maximum lengths in the database, validated with Django's null-character validator and a visible-character check. Pages list them by ascending ID, which is creation order because a round's writes are serialised by its row lock.
- **Case–criterion link:** a many-to-many link between a case and criteria of the same round, through an explicit link model (`rounds.CaseCriterion`) with a unique constraint on case and criterion, because Django's automatic link table cascades deletes. The case form's choices are the URL round's criteria, so an ID of another round or workspace, a missing ID or a non-integer value gets the [RND-2.7](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases) message, and a repeated ID counts once. The write transaction checks the chosen IDs against the round again after locking it, with the same message.
- **Criterion and case writes:** functions in `rounds.services`, called inside the view's transaction after it locks the round row and re-checks the Draft state. Adding enforces the caps of 20 criteria and 30 cases ([RND-2.5](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases)); saving a case replaces its links with the chosen ones; deleting a criterion first checks that no case links to it ([RND-2.6](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases)). A criterion or case deleted after its form was opened gets the 404 when saved.
- **Build:** a round, a label, a comparison key (the label with format characters, Unicode category Cf, removed and then NFC-normalised), its creation time and the cases it covers, with a database unique constraint on round and comparison key ([RND-5.3](product/rounds.md#rnd-5-request-a-retest)). Publishing creates the first build covering every case; a retest request is stored as a build covering the selected cases. A case's current build is the newest build covering it. The model is `rounds.Build`, with a label of at most 100 characters and a key of at most 300, because NFC can lengthen text up to three times; one function, `rounds.services.build_key(label)`, computes the key. Covered cases go through an explicit link model, `rounds.BuildCase`, with `PROTECT` keys and a unique constraint on build and case. Builds are ordered by ascending ID, which is creation order under the round lock, so a case's current build is the highest-ID build covering it.
- **Publishing:** the publish route validates the label with a form whose one field, "Build label", uses the shared text field (at most 100 characters) and a text input with `dir="auto"`; an invalid label re-renders the round page with status 200. Otherwise, in one transaction, the view locks the round row and re-checks the Draft state (409), then calls `rounds.services.publish(round_, label)`. That function refuses a round with no cases with the [RND-3.3](product/rounds.md#rnd-3-publish-a-round-to-beta-testers) message (the round page again, status 200), and otherwise creates the first build covering every case of the round, sets the state to Open and sets the publication time. After the commit, the view adds "Round published." through Django's messages and redirects to the round page.
- **Closing:** the close route takes no form fields. In one transaction, the view locks the round row and re-checks the Open state (409 for Draft or Closed, so of two racing closes the second gets 409 once the first commits), then calls `rounds.services.close(round_)`, which sets the state to Closed and the closing time in one update that matches only an Open round, and raises an error with fixed text if no row changed. After the commit, the view adds "Round closed." through Django's messages and redirects to the round page. Nothing sets a Closed round's state again.
- **Retesting:** the retest route's form (`rounds.forms.RetestForm`) has a "Test cases to retest" field whose choices are the URL round's cases, as checkboxes labelled with their titles in creation order, so an ID of another round or workspace, a missing ID or a non-integer value gets the [RND-5.6](product/rounds.md#rnd-5-request-a-retest) message, no selection the RND-5.2 one, and a repeated ID counts once; and a "Build label" field like publishing's. A GET or POST to a Draft or Closed round gets 409 before the form. An invalid form re-renders the retest page with status 200. Otherwise, in one transaction, the view locks the round row through the workspace lookup and re-checks the Open state (409), then calls `rounds.services.request_retest(round_, label, case_ids)`. That function, before any write, refuses a round that is not Open with `RoundNotOpen` (which the view turns into the 409, never a 500), then refuses with `Refused` and the field it belongs to: 10 builds already (RND-5.4), any ID not a case of the locked round (RND-5.6, since nothing in the database ties a `BuildCase`'s case to its build's round), and a label whose `build_key` matches one of the round's builds (RND-5.3); refusal and error texts carry no label. It then creates the build and one `BuildCase` per distinct case and returns the build. Because the duplicate check runs under the lock, two racing requests with one label meet the check, not the unique constraint, so no database error detail with a label is logged; the constraint remains a backstop. The view catches refusals outside the committing transaction and shows them next to their field. After the commit, it adds the RND-5.1 message through Django's messages, with the extra tag `retest`, and redirects to the round page. The round page and the sign-in page show a `retest` message as its fixed text with only the label, the part between the fixed "on build " and the final full stop, passed through the per-line rendering filter; other messages show as before. Each selected case's current build becomes the new build by the current-build rule above.
- **Results (RES), provisional:** a result will reference one case and one build of the same round that covers the case, so its criteria are the case's frozen links. The result itself is specified in [RES](product/results.md).
- **Deletion:** every foreign key here, including those from results, uses `PROTECT`. Deleting a case first deletes its links explicitly in the same transaction; a linked criterion is not deleted. Criteria and cases can be deleted only while Draft, before any build or result exists.
- **Writes:** every round change runs in one transaction that locks the round row (`select_for_update`), then re-checks the state, caps, label uniqueness and that submitted records are in the round. Creating a round locks the workspace row to check the round cap. Provisionally, creating or changing a result (RES) also locks the round row, then re-checks the state, that the build is in the round and covers the case, and that it is the case's current build. Concurrent Draft edits to the same record are not merged; the last saved edit wins.
- **Storage failure:** a rounds route that raises Django's `DatabaseError` rolls back its transaction, logs the exception with its traceback, and renders `503.html` with status 503 ([rules for every round action](product/rounds.md#rules-for-every-round-action)). The round list on the Coordinator home follows the [accounts routes](#accounts-routes) storage rule, because that page is an accounts route.
- **Rendering:** a template filter removes the bidi controls U+202A to U+202E and U+2066 to U+2069 from user text used in a `<title>`, replaces each line break (any separator below) with a space, and wraps the result in U+2068 and U+2069; Django's autoescaping still applies. In page content, a second filter splits user text into lines at every separator Python's `str.splitlines()` recognises (line feed, U+000B vertical tab, U+000C form feed, carriage return, U+001C to U+001E, U+0085, U+2028 and U+2029), escapes each line, wraps it in its own `<span dir="auto">` and joins the lines with `<br>`, so no separator character is output and each line's direction is isolated ([rendering rule](product/rounds.md#rules-for-every-round-action)).
- **Sample round:** fixed synthetic text, written by the shared round-creation code inside the [demo creation](#accounts-and-workspaces) transaction ([RND-7](product/rounds.md#rnd-7-sample-draft-round-in-a-new-demo-workspace)).

## Routes

### Foundation route

`/` is a public GET/HEAD route rendering `home.html`, with no input and no writes. Other methods return 405; unresolved paths and uncaught exceptions use generic nondebug 404/500 responses, the 404 rendering `404.html` from ACC-2. Its observable contract is [PLT-1](product/platform.md#plt-1-django-foundation-and-continuous-verification); from ACC-1 the page also links to `/sign-in/` (PLT-1.1). From ACC-2 it reads the session to redirect a signed-in user to their role home, and its button's form carries Django's CSRF token, which sets the CSRF cookie; the view stays CSRF-exempt so other methods keep PLT-1.2's 405. Future routes must define authorization, validation and state contracts before implementation.

The accounts and rounds routes below are planned for their implementation slices; ACC-2 turns `/` into the accounts start page in the table below. Each route contract must name its method, role/workspace/ownership checks, input validation, state preconditions, success result and denied/failure behaviour before implementation.

### Accounts routes

For [ACC](product/accounts.md). Every POST uses Django's CSRF protection, which also rejects an `Origin` header naming another origin, with 403 ([ACC-1.8](product/accounts.md#acc-1-sign-in-and-out-by-role), [ACC-2.7](product/accounts.md#acc-2-create-an-isolated-demo-workspace)). A storage failure in demo creation, or in sign-in from its pre-check through its [limited transaction](#accounts-and-workspaces), authentication included, gives the 503 page of [ACC-2.5](product/accounts.md#acc-2-create-an-isolated-demo-workspace) and changes nothing; other storage failures on these routes, including starting the session after a successful sign-in, give the generic 500 of PLT-1.3. Sign-out deletes the old session row and then creates a new one for its message, so a failure to create it leaves the session ended with the generic 500 ([persistence decision](#data-model)).

| --- | --- | --- | --- | --- |
| `/` | GET, HEAD | Signed out | Relay start page, titled "Relay", with a sign-in link and the "Create a demo workspace" button | Signed in: redirect to own role home |
| `/sign-in/` | GET, POST | Anyone | GET shows the form, unlimited. POST first reads the per-address count unlocked and refuses if its limit has been reached, then validates the fields with a form: surrounding whitespace is removed from the username, which may have at most 150 characters, and neither field may contain a NUL character. An invalid field is a failed sign-in, counted under [ACC-3.3](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation), with the ACC-1.2 failure. Django's authentication then checks the username and password outside any lock; one transaction then locks the count, refuses if its limit has been reached meanwhile, and records a failure ([limited transactions](#accounts-and-workspaces)); success starts a new session and redirects to own role home, ignoring `next` ([ACC-1.1, 1.2, 1.7](product/accounts.md#acc-1-sign-in-and-out-by-role)) | Invalid: [ACC-1.2](product/accounts.md#acc-1-sign-in-and-out-by-role); limited: the sign-in page with status 429 and the [ACC-3.1](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation) message in place of the failure message; storage: [ACC-3.7](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation) |
| `/sign-out/` | POST | Anyone | Flushes the session and redirects to `/sign-in/`, which shows "You have signed out." once through Django's messages if the visitor was signed in, and no message otherwise ([ACC-1.5](product/accounts.md#acc-1-sign-in-and-out-by-role)) | Other methods: 405 |

| `/coordinator/` | GET | Test Coordinator | "Coordinator home" | Signed out: redirect to `/sign-in/`; Beta Tester: 403 of [ACC-1.4](product/accounts.md#acc-1-sign-in-and-out-by-role) |
| `/tester/` | GET | Beta Tester | "Tester home" | Signed out: redirect to `/sign-in/`; Test Coordinator: 403 of ACC-1.4 |

The session cookie is `HttpOnly`; session and CSRF cookies are `SameSite=Lax`, and `Secure` outside local development (shared settings set `Secure`; `relay.settings.local` turns it off). Django's messages use session storage (`MESSAGE_STORAGE` is `django.contrib.messages.storage.session.SessionStorage` in the shared settings), so a message is kept in the session row until shown, no response sets a `messages` cookie and one sent by a browser is ignored. `/sign-in/`, `/coordinator/` and `/tester/` are never cached (`Cache-Control: private, no-store`).

Signed-out redirects go to `/sign-in/` with no `next` parameter.

Delivery order: ACC-1 builds `/sign-in/` (page title "Sign in"), `/sign-out/`, `/coordinator/` and `/tester/`, and adds the sign-in link to the foundation's `/` (PLT-1.1). ACC-2 adds `/demo/`, the start page's button and its signed-in redirect, the 503 page and the 404 page; ACC-3 adds the limit counts, their locks and timeouts, the 429 responses and the sign-in 503. Until ACC-3, a storage failure on an accounts route gives the generic 500 of PLT-1.3, except a failure inside `/demo/`'s creation block, which gives the 503; `/demo/`'s signed-in check and password generation run before that block.

### Rounds routes

For [RND](product/rounds.md). Every route requires a signed-in Test Coordinator and applies the [rules for every round action](product/rounds.md#rules-for-every-round-action) in their order; Django's CSRF middleware runs before the view, so an unsafe request without a valid token or with a foreign `Origin` gets 403 before any 405 or sign-in redirect; a state not listed below gets their 409. Invalid input re-renders the form, and a refused delete or publish the round page, with status 200 and the message. A successful POST redirects to the round page, which shows the criterion's success message, if any, once. The Coordinator home (`/coordinator/`) also lists the workspace's rounds. `<round>`, `<criterion>` and `<case>` are integer IDs; no route takes a build ID. A route accepts exactly the methods listed, so HEAD gets 405 where only GET is listed. The 409 page is titled "Action not available", with the state message as its heading. Rounds pages and their 405, 409 and 503 responses are never cached (`Cache-Control: private, no-store`), like the role homes; their 403 and 404 pages show fixed text only. A storage failure while loading the session or user on a rounds route also gives the 503, before any round is read. Saving the session after the view, to store a success message or drop one just shown, happens in Django's session middleware, outside the view's 503 handling: Django turns any failure to save an existing session row, including one ended by a concurrent sign-out, into `SessionInterrupted`, so the response is its default "Bad Request (400)" page, logged as a warning, with a change the view has already committed kept and its message lost. Only a failure to create a new session row, as at sign-out, gives the generic 500 of [PLT-1.3](product/platform.md#plt-1-django-foundation-and-continuous-verification). It is a residual of keeping messages in the session, accepted by the human on 2026-10-27 (#57) and recorded in the [security spec](SECURITY-SPEC.md#rounds-observations-and-history).

## Configuration

The `.env.example` file may contain only empty placeholders and throwaway local database values. Settings never load dotenv files. `relay.settings.local` reads `DJANGO_SECRET_KEY` (required/nonblank), `DJANGO_DEBUG` (strict true/false; defaults false), `DJANGO_ALLOWED_HOSTS` (comma-separated localhost/127.0.0.1/[::1] only), and `POSTGRES_HOST/PORT/DB/USER/PASSWORD` (defaults localhost/5432/relay/relay/relay). Database host must be localhost, 127.0.0.1 or ::1. These local settings cannot configure a hosted runtime. `manage.py` and WSGI default to local settings; explicit `DJANGO_SETTINGS_MODULE` remains supported.

`relay.settings.test` imports only shared settings and uses fixed non-secret values: PostgreSQL database/user/password `relay_test`, host 127.0.0.1, port 55432, test database `test_relay_test`, debug false and hosts testserver/localhost/127.0.0.1. `pytest.ini` selects these settings; tests use no provider. The test role needs database creation permission on its throwaway server. ACC-1 adds the first business migrations.

Both database configurations explicitly set libpq `hostaddr` through Django's database `OPTIONS`, preventing inherited `PGHOSTADDR` from redirecting connections. Local localhost/127.0.0.1 map to 127.0.0.1; local ::1 maps to ::1. Tests fix the address to 127.0.0.1.

In every environment, the shared settings install Django's `XFrameOptionsMiddleware` first, above `SecurityMiddleware`, so every response Django makes refuses framing (`X-Frame-Options: DENY`): pages, error pages, and responses other middleware makes, such as an HTTPS redirect, the 400 for a disallowed host or a failed session save, and the 500 when a new session row cannot be created. No view is exempt, and no code sets the header or `X_FRAME_OPTIONS` itself, so Django's default `DENY` applies (#58). Responses served outside Django, such as the platform's own error pages, are not covered.

Production settings, checked before release:

- `DEBUG` off; `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` list only the production host and origin, with no wildcard.
- HTTPS is detected through `SECURE_PROXY_SSL_HEADER` only once Vercel's forwarded-protocol header is verified under the [release gate](#release-verification).
- HSTS is on.
- Production keeps the shared middleware, with `XFrameOptionsMiddleware` first, and its responses carry `X-Frame-Options: DENY`.

## Release verification

Delivery will verify the final candidate before a controlled production deployment, then run smoke checks. Deployment workflows, migration handling, checked-source provenance, failure recovery and smoke-check contracts remain to be designed and tested. The scaffold does not claim any release controls are configured.

Release gate: production is not released until Vercel's actual client-address source, forwarded-protocol header and function time limit are verified and recorded (the time limit must be at least 30 seconds, above the [limit timeouts](#accounts-and-workspaces) plus a password hash), the production database's connection limit and pooler mode are recorded, and the production settings under [Configuration](#configuration) are checked. The client-address source is verified by observation, not by reading documentation: from two external clients, requests with forged `X-Forwarded-For`, `X-Real-IP` and `Forwarded` headers must produce stored keys that follow each client's real address, and no production request may use the `unknown` key.
