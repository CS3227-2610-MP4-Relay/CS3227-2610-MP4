# Technical spec

How Relay will be built and run. What it will do is in [`PRODUCT-SPEC.md`](PRODUCT-SPEC.md). The application runs locally and in CI only. Workspaces, accounts and sessions (ACC-1), demo workspace creation (ACC-2), abuse-limit counters (ACC-3), test rounds with their title and state (RND-1), their acceptance criteria, test cases and links (RND-2), builds with publishing (RND-3), retests as further builds (RND-5), closing with its closing time (RND-6), each new demo workspace's sample round (RND-7), and the AI gateway with its operational rows and drafting pages (RND-8) exist; live AI call status belongs in the [gateway contract](ai/llm-gateway.md#live-switch); other business schema and hosted application environments remain planned.

## Architecture

- One Django project that renders HTML on the server, with no separate front end. Application code and its tests will live under `src/`.
- PostgreSQL for application storage and database-backed tests.
- Configuration from environment variables, with no committed credentials.
- SoC LLM through one shared gateway; feature code selects authorized context before invoking it. The boundary is built; its live-call status and contract are in [`ai/llm-gateway.md`](ai/llm-gateway.md).

`src/manage.py` starts the `relay` Django project; `relay.wsgi` is its WSGI entry point and `relay.pages` owns public presentation. Shared templates live in `src/relay/templates/`. The `accounts` app (`src/accounts/`) owns the [workspace and account models](#accounts-and-workspaces) and the accounts routes, with Django's `auth`, `contenttypes`, `sessions` and `messages` apps; `django.contrib.admin` is never installed. The `rounds` app (`src/rounds/`), added by RND-1, owns the [round models](#rounds) and the [rounds routes](#rounds-routes). The `ai` app (`src/ai/`) owns the [gateway's rows](#ai-gateway), the gateway and the RND-8 drafting views. ACC-1 adds the accounts apps; until then no auth/session apps or business models are installed. Runtime and dependency pins belong in the root configuration files.

## Data model

Only the subsections below are specified. Design workspaces, role-based accounts, rounds, requirements, cases, build references and results around the [product areas](PRODUCT-SPEC.md#areas). Before schema implementation, settle ownership, state transitions, published-case edits, submitted-observation edits and result-history/version rules. Do not infer these from a proposed screen or table name.

Persistence and retention, decided for ACC-1 (see its [plan](../plans/2-sign-in-by-role.md)):

- Workspaces, accounts, rounds, results, limit rows and their hashed address keys are kept for the life of the course deployment. Nothing expires or is deleted automatically, and there is no cleanup subsystem, except that the gateway deletes its own quota records once they leave their rolling window ([AI gateway](#ai-gateway)); they hold no user text.
- An expired session is refused by its absolute expiry; its row is not deleted automatically. Signing out a signed-in user deletes their session row, then the sign-out message starts a new anonymous session row, which expires after 8 hours, is emptied once the message is shown, and is replaced at the browser's next sign-in. A signed-out visitor's sign-out, and viewing the sign-in page, create no row.
- When shared storage is exhausted, a failed write is not retried, and the user gets that route's existing error page: the generic 500 of [PLT-1.3](product/platform.md#plt-1-django-foundation-and-continuous-verification), or the 503 page that [ACC-2.5](product/accounts.md#acc-2-create-an-isolated-demo-workspace) and [ACC-3.7](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation) define. Saving the session at the end of a request is the exception: a failed save of an existing session row gives Django's "Bad Request (400)", and a failed creation of a new one, as at sign-out, the generic 500 ([rounds routes](#rounds-routes)). A route that writes in a transaction rolls the whole transaction back. Existing records, including result history, are never deleted or overwritten to make room.
- Before peer testing, an operator checks the hosting database's storage use. Exhaustion and unbounded session and counter growth are [accepted residual risks](SECURITY-SPEC.md#sign-in-and-access-control) for the course deployment.

### Accounts and workspaces

For [ACC](product/accounts.md). Retention follows the [persistence decision](#data-model) above.

- **Workspace:** a unique name, `Demo workspace <suffix>`, and its creation time. Every workspace-owned record has a non-null workspace reference. Routes check the role first, then look records up through one shared helper that filters by the signed-in user's workspace before reading and gives the 404 of [ACC-2.4](product/accounts.md#acc-2-create-an-isolated-demo-workspace) for any other workspace's record.
- **Workspace lookup helper:** `accounts.workspaces.workspace_records(user, model)` returns `model`'s records whose `workspace` is the user's workspace. A route reads a URL-named record with `get_object_or_404` on that queryset, so another workspace's record raises the same `Http404` as a missing one; a form uses that queryset for its choice field, so another workspace's ID gets the field's invalid-choice message. Every 404, including unresolved paths, renders `404.html` with "Page not found." From RND-1 the rounds views and the Coordinator home's round list use the helper.
- **Account:** a custom Django user model (`accounts.User`, the `AUTH_USER_MODEL`), added by ACC-1 before any persistent database (in particular production, under #5) is migrated. It has a globally unique username, a Django password hash, a non-null workspace (`PROTECT`) and a role of `coordinator` or `tester`, all fixed at creation, plus Django's last-sign-in time. The model has no staff, superuser or permission fields, and `django.contrib.admin` is not installed, so there is no admin route.
- **Generated credentials:** usernames are `coord-<suffix>`, `tester1-<suffix>` and `tester2-<suffix>`, sharing the workspace's suffix of 8 random lowercase letters and digits. A new suffix is drawn while the workspace name or any of the three usernames already exists, up to 3 draws; if the last one also exists, or a concurrent creation takes it first, the unique constraint fails and ACC-2.5 applies. Each password is 16 random characters from `a-z`, `A-Z` and `0-9`, generated with `secrets` and hashed before any lock is taken. Plain passwords exist only in memory while rendering the creation response.
- **Creation:** one transaction holds the limit counts, the workspace, its accounts, its sample round and the rendering of the creation response, so any failure rolls everything back ([ACC-2.5](product/accounts.md#acc-2-create-an-isolated-demo-workspace)). The `/demo/` view first reads both creation counts without locking them and, if either has reached its limit, gives the 429 of [ACC-3.4](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation) before generating anything, so a refused request costs no password hashing. Otherwise it generates and hashes the passwords, then opens one `transaction.atomic()` block. Inside it, the view calls `limits.start()`, locks both counts and checks them again, giving the same 429 if either has been reached meanwhile; one function, `accounts.demo.create_demo_workspace`, writes the workspace, its accounts and its [sample round](#rounds) in a savepoint, so it is also all-or-nothing on its own; and the view renders the page to a string. The view then records the creation in both counts. The response is built from that string only after the block commits, with `Cache-Control: no-store`. Either 429 is returned as a normal response, never raised through the block's exception handler. Any other exception in the block, from storage, the commit or rendering, rolls back and gives the 503 page (`503.html`, status 503); the view logs the exception with its traceback only, never the passwords or the rendered page. A constraint violation's message may name an existing username or workspace name, never a plain password. Plain passwords are Django sensitive variables in the creating functions, and a credential's repr hides its password, so error reports with frame variables do not show them either.
- **Limit counter:** `accounts.LimitCounter`, one row per scope and key, holding a window start and a count, unique on scope and key. The scopes are `sign-in` (per address: 30 per 15 minutes), `demo` (per address: 10 per hour) and `demo-total` (one row, key `all`: 200 per 24 hours), as in [ACC-3](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation). A migration creates the `demo-total` row. A count has reached its limit while it is at least the limit and the current time is before its window start plus its window; at or after that time it counts as 0. Recording a counted request sets the window start to now and the count to 1 if the count is 0 or the window has ended, and otherwise adds 1. Refused requests change no count or window start (ACC-3.3). The current time is `django.utils.timezone.now()`, so tests control it with `unittest.mock`.
- **Limit service:** `accounts.limits` defines the three limits and these functions, the only ones the views call:
  - `client_key(request)` returns the stored key of the client address (below).
  - `peek(limit, key)` reads a count without locking, for the sign-in and `/demo/` pre-checks; a missing row counts as 0.
  - `start()` sets, for the current transaction only (`set_config(..., true)`), `lock_timeout` to 5 seconds, `statement_timeout` to 10 seconds and `idle_in_transaction_session_timeout` to 10 seconds. Each limited transaction calls it first.
  - `lock(limit, key)` inserts the row with count 0, or else locks the existing row unchanged, in one `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` statement, and returns the locked row.
  - `reached(counter, limit)` and `record(counter, limit)` apply the rules above.
- **Limited transactions:** a creation locks its `demo` row, then the `demo-total` row. A sign-in POST first reads its `sign-in` count unlocked and, if the limit has been reached, refuses without validating the form or checking the password. Otherwise it validates the form and authenticates outside any transaction or lock, then opens one `transaction.atomic()` block that calls `start()`, locks its `sign-in` row, checks it again (refusing even a correct password if the limit was reached meanwhile) and records any failure, so concurrent attempts cannot overshoot and a rollback records nothing. No password is hashed while any counter lock is held. The session is started only after the block commits, so a failure in the block signs no one in. PostgreSQL counts the session as idle while Python works, so the idle timeout is longer than the work done while a lock is held: the re-check and recording during sign-in, and writing and rendering during demo creation, whose passwords are hashed first. PostgreSQL 17's `transaction_timeout` is not used: the statement and idle timeouts already guarantee that a lock is released. In `/demo/`, any exception from the pre-check through the creation block, password hashing included, gives the 503, as in [Creation](#accounts-and-workspaces); in sign-in, any `django.db.Error` from the pre-check through its transaction, authentication included, does. Either case covers a lock, statement or idle timeout and a failed commit, rolls back, and gives the 503 of [ACC-3.7](product/accounts.md#acc-3-limit-abuse-of-sign-in-and-demo-workspace-creation), logged with its traceback only. The timeouts must stay below the platform's function time limit, which is verified under the [release gate](#release-verification).
- **Client address:** `REMOTE_ADDR`, never a client-supplied forwarding header. IPv4 addresses count individually, an IPv4-mapped IPv6 address as its IPv4 address, and other IPv6 addresses by their `/64` prefix; a missing or unparseable address uses the fixed value `unknown`. The stored key is the hex SHA-256 `salted_hmac` of that value (the address, the prefix or `unknown`) with its own salt, never the address itself. Production depends on the client-address gate under [Release verification](#release-verification); a trusted-proxy header setting is a separate decision, needed only if that verification shows it.
- **Sessions:** Django's database-backed sessions. Sign-in sets an absolute expiry time 8 hours ahead, so later session writes cannot extend it ([ACC-1.6](product/accounts.md#acc-1-sign-in-and-out-by-role)); signing out a signed-in user deletes the session row, and the sign-out message then lives in a new anonymous session. Expired rows are not deleted automatically ([persistence decision](#data-model)).

### Rounds

For [RND](product/rounds.md). Field limits, caps and messages are in its criteria. Nothing here deletes a round, build or result; retention and full storage follow the [persistence decision](#data-model). A round belongs to one workspace and every other record below to one round. URL records are looked up through the workspace helper, then checked to be in the round the URL names; form-submitted IDs are checked against the round in the form's validation ([checking order](product/rounds.md#rules-for-every-round-action)).

- **Round:** a non-null workspace, a title of at most 120 characters, a state of `draft`, `open` or `closed` (a database check constraint), and its creation time; RND-3 adds its publication time (`published_at`, empty while Draft, set when publishing) and RND-6 its closing time (`closed_at`, empty until closing, set when closing). Lists order rounds by creation time, newest first, then by descending ID.
- **Round creation:** one function, `rounds.services.create_round(workspace, title)`, used by the new-round route and by the [demo creation](#accounts-and-workspaces) transaction for the sample round (RND-7). Its workspace argument is only ever `request.user.workspace` or the workspace ACC-2 has just created, never a value from request data. In a transaction, it locks the workspace row, counts the workspace's rounds, and creates a Draft round below the cap of 20 or raises an error the view shows as the [RND-1.4](product/rounds.md#rnd-1-prepare-a-test-round) message.
- **Text fields:** one form field, `rounds.forms.RoundTextField`, serves every round text field. It replaces each CR LF pair with LF, so a line break typed in a browser counts as one character, trims surrounding whitespace with Python's `str.strip()` and counts characters (code points). It applies the length limits and Django's null-character validator, then the visible-character check: a character is visible unless `str.isspace()` is true for it or its Unicode category is Cc or Cf, and text without a visible character is treated as empty. Only if those pass does it apply the direction check, which refuses text containing a text-direction control ([rule 5](product/rounds.md#rules-for-every-round-action)) and no other character. Services and models do not repeat the direction check, so rendering still treats stored text as untrusted. Criterion text, steps and expected result use a `<textarea>`; every round text input carries `dir="auto"`.
- **Acceptance criterion** (`rounds.Criterion`) and **test case** (`rounds.Case`): a non-null round and their text fields ([RND-2.4](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases)), with those maximum lengths in the database, validated with Django's null-character validator and a visible-character check. Pages list them by ascending ID, which is creation order because a round's writes are serialised by its row lock.
- **Case–criterion link:** a many-to-many link between a case and criteria of the same round, through an explicit link model (`rounds.CaseCriterion`) with a unique constraint on case and criterion, because Django's automatic link table cascades deletes. The case form's choices are the URL round's criteria, so an ID of another round or workspace, a missing ID or a non-integer value gets the [RND-2.7](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases) message, and a repeated ID counts once. The write transaction checks the chosen IDs against the round again after locking it, with the same message.
- **Criterion and case writes:** functions in `rounds.services`, called inside the view's transaction after it locks the round row and re-checks the Draft state. Adding enforces the caps of 20 criteria and 30 cases ([RND-2.5](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases)); saving a case replaces its links with the chosen ones; deleting a criterion first checks that no case links to it ([RND-2.6](product/rounds.md#rnd-2-manage-acceptance-criteria-and-test-cases)). A criterion or case deleted after its form was opened gets the 404 when saved.
- **Build:** a round, a label, a comparison key (the label with format characters, Unicode category Cf, removed and then NFC-normalised), its creation time and the cases it covers, with a database unique constraint on round and comparison key ([RND-5.3](product/rounds.md#rnd-5-request-a-retest)). Publishing creates the first build covering every case; a retest request is stored as a build covering the selected cases. A case's current build is the newest build covering it. The model is `rounds.Build`, with a label of at most 100 characters and a key of at most 300, because NFC can lengthen text up to three times; one function, `rounds.services.build_key(label)`, computes the key. Covered cases go through an explicit link model, `rounds.BuildCase`, with `PROTECT` keys and a unique constraint on build and case. Builds are ordered by ascending ID, which is creation order under the round lock, so a case's current build is the highest-ID build covering it.
- **Publishing:** the publish route validates the label with a form whose one field, "Build label", uses the shared text field (at most 100 characters) and a text input with `dir="auto"`; an invalid label re-renders the round page with status 200. Otherwise, in one transaction, the view locks the round row and re-checks the Draft state (409), then calls `rounds.services.publish(round_, label)`. That function refuses a round with no cases with the [RND-3.3](product/rounds.md#rnd-3-publish-a-round-to-beta-testers) message (the round page again, status 200), and otherwise creates the first build covering every case of the round, sets the state to Open and sets the publication time. After the commit, the view adds "Round published." through Django's messages and redirects to the round page.
- **Closing:** the close route takes no form fields. In one transaction, the view locks the round row and re-checks the Open state (409 for Draft or Closed, so of two racing closes the second gets 409 once the first commits), then calls `rounds.services.close(round_)`, which sets the state to Closed and the closing time in one update that matches only an Open round, and raises an error with fixed text if no row changed. After the commit, the view adds "Round closed." through Django's messages and redirects to the round page. Nothing sets a Closed round's state again.
- **Retesting:** the retest route's form (`rounds.forms.RetestForm`) has a "Test cases to retest" field whose choices are the URL round's cases, as checkboxes labelled with their titles in creation order, so an ID of another round or workspace, a missing ID or a non-integer value gets the [RND-5.6](product/rounds.md#rnd-5-request-a-retest) message, no selection the RND-5.2 one, and a repeated ID counts once; and a "Build label" field like publishing's. A GET or POST to a Draft or Closed round gets 409 before the form. An invalid form re-renders the retest page with status 200. Otherwise, in one transaction, the view locks the round row through the workspace lookup and re-checks the Open state (409), then calls `rounds.services.request_retest(round_, label, case_ids)`. That function, before any write, refuses a round that is not Open with `RoundNotOpen` (which the view turns into the 409, never a 500), then refuses with `Refused` and the field it belongs to: 10 builds already (RND-5.4), any ID not a case of the locked round (RND-5.6, since nothing in the database ties a `BuildCase`'s case to its build's round), and a label whose `build_key` matches one of the round's builds (RND-5.3); refusal and error texts carry no label. It then creates the build and one `BuildCase` per distinct case and returns the build. Because the duplicate check runs under the lock, two racing requests with one label meet the check, not the unique constraint, so no database error detail with a label is logged; the constraint remains a backstop. The view catches refusals outside the committing transaction and shows them next to their field. After the commit, it adds the RND-5.1 message through Django's messages, with the extra tag `retest`, and redirects to the round page. The round page and the sign-in page show a `retest` message as its fixed text with only the label, the part between the fixed "on build " and the final full stop, passed through the per-line rendering filter; other messages show as before. Each selected case's current build becomes the new build by the current-build rule above.
- **Result (`rounds.Result`):** one tester foreign key to `AUTH_USER_MODEL`, one case and one build, all `PROTECT`; outcome stored as `pass` or `fail`, an observation of at most 2000 characters (empty allowed), and nullable `submitted_at`. A database unique constraint on tester/case/build permits only one draft or submission per tuple; a database check constrains outcome. No result deletion is offered. Build/case same-round coverage, tester role/workspace and current-build membership are checked by the write service; the case's frozen links supply its criteria. Existing workspace case/build caps plus tuple uniqueness bound result rows per tester. Submission sets the timestamp once and thereafter the service refuses every write ([RES-2](product/results.md#res-2-save-and-submit-an-outcome-with-observations)).
- **Deletion:** every foreign key here, including those from results, uses `PROTECT`. Deleting a case first deletes its links explicitly in the same transaction; a linked criterion is not deleted. Criteria and cases can be deleted only while Draft, before any build or result exists.
- **Writes:** every round change runs in one transaction that locks the round row (`select_for_update`), then re-checks the state, caps, label uniqueness and that submitted records are in the round. Creating a round locks the workspace row to check the round cap. Result persistence uses the same round lock and checks the authenticated tester's workspace, case/build membership and coverage, Open state, current build and existing submission before validating and writing; these checks and the result write share one transaction. Concurrent Draft edits to the same record are not merged; the last saved edit wins. Result drafts follow the serialized-write rules in RES-2.5.
- **Storage failure:** a rounds route that raises Django's `DatabaseError` rolls back its transaction, logs the exception with its traceback, and renders `503.html` with status 503 ([rules for every round action](product/rounds.md#rules-for-every-round-action)). The round list on the Coordinator home follows the [accounts routes](#accounts-routes) storage rule, because that page is an accounts route.
- **Rendering:** a template filter removes the text-direction controls of [rule 5](product/rounds.md#rules-for-every-round-action) (U+202A to U+202E and U+2066 to U+2069, one set shared with the form's direction check) from user text used in a `<title>`, replaces each line break (any separator below) with a space, and wraps the result in U+2068 and U+2069; Django's autoescaping still applies. In page content, a second filter splits user text into lines at every separator Python's `str.splitlines()` recognises (line feed, U+000B vertical tab, U+000C form feed, carriage return, U+001C to U+001E, U+0085, U+2028 and U+2029), escapes each line, wraps it in its own `<span dir="auto">` and joins the lines with `<br>`, so no separator character is output and each line's direction is isolated ([rendering rule](product/rounds.md#rules-for-every-round-action)).
- **Sample round:** `rounds.sample.create_sample_round(workspace)`, called by `accounts.demo.create_demo_workspace` with the workspace it has just written, inside the [demo creation](#accounts-and-workspaces) transaction after its limit locks ([RND-7](product/rounds.md#rnd-7-sample-draft-round-in-a-new-demo-workspace)). It creates the round with `create_round`, which locks the new workspace row and applies the round cap, locks the new round row, then adds the criteria and cases with `add_criterion` and `add_case`, so the RND-2 caps and same-round links are enforced as for the coordinator's own writes. These rows are not yet committed, so no other transaction can wait on their locks. The fixed synthetic text, ASCII only and within the RND-2 limits, has its one home in the constants of `rounds.sample`; a storage failure in any of these writes rolls the whole creation back ([ACC-2.5](product/accounts.md#acc-2-create-an-isolated-demo-workspace)).
- **AI drafting:** [RND-8](product/rounds.md#rnd-8-draft-test-cases-with-ai) adds no model or table; the gateway's rows are [below](#ai-gateway). The drafting view checks the selection with a form whose choices are the URL round's criteria, as the retest form does, and counts the round's cases, with no lock held; it then builds the data part with a JSON encoder, closes its database connection, then calls the [shared gateway](ai/llm-gateway.md) once, outside any transaction, and validates the reply as the [test-drafting contract](ai/test-drafting.md) requires before rendering. "Use this draft" posts the draft's text and criterion IDs as hidden fields to a view that cleans the text again, checks the URL round's criteria whose IDs equal a posted value as strings, without looking up any posted value, and renders the RND-2 case form with them as initial values, unvalidated; that form submits to the normal new-case route. Neither view writes to the database. Like the demo creation's credentials, the criteria text, instructions, data part and reply are sensitive variables in the drafting functions, and both views mark their POST fields with `sensitive_post_parameters`, so error reports show none of them; log records carry only fixed codes. A `DatabaseError` raised by the gateway's reservation or release reaches the rounds storage-failure rule (503); any other gateway exception gives the RND-8.4 unavailable message.

**Observation feedback:** [RES-4](product/results.md#res-4-suggest-missing-details-in-a-draft-observation) adds no schema. `ai.feedback` owns request-local source snapshots/encoding and strict reply validation, reusing `ai.drafting.clean`; `ai.feedback_views` reuses `rounds.tester.tester_view` and `rounds.results.entry(..., write=False)`. Fully materialize authorized case criteria constrained to the round before leaving that short read transaction. Close the database connection before the gateway call and hold no transaction or row lock during it. Re-enter the same authorization/read operation afterwards and compare the raw source snapshot, without a persisted fingerprint or revision field. Render only after this recheck, with the original source and validated questions; mark sensitive variables/POST values and log only fixed codes. Gateway accounting storage errors propagate to the tester wrapper; other gateway failures follow the [AI contract](ai/observation-feedback.md). This read/check design detects changed current values, not edits that changed and then returned to identical values.

### AI gateway

For the [shared gateway](ai/llm-gateway.md#limits-and-accounting), whose limits are proposals pending confirmation. Neither table holds prompt, source or reply text.

- **Call slot** (`ai.CallSlot`): a scope, a key and an expiry time, unique on scope and key. Scope `user` has one row per user who has called the gateway, keyed by the user's ID and created at their first call; scope `deployment` has two fixed rows, keys `0` and `1`, created by a migration. A slot is free once its expiry has passed. Rows are kept for the life of the deployment.
- **Call record** (`ai.CallRecord`): a scope (`user-calls`, keyed by user ID, or `deployment-calls`, key `all`), a key and a creation time, indexed on all three. Each counted call adds one row per scope. Nullable nonnegative big-integer fields `prompt_tokens`, `completion_tokens`, `total_tokens` and `elapsed_ms` hold the [gateway accounting contract's](ai/llm-gateway.md#usage-and-latency) metrics; existing rows migrate as null. Both rows represent the same call, so aggregate only one scope. Reservation returns both record IDs along with its existing slots/start; completion updates those IDs atomically without holding a transaction across provider work. While reserving a call, the gateway deletes that scope and key's rows older than the window, so a user's old rows remain until that user calls again.
- **Reservation:** one transaction locks the user's slot (creating it if missing) and both deployment slots with `select_for_update`, in that order, then checks and records both quotas, then sets the slots' expiry. Release, after the call, clears each slot with an update that matches only this call's expiry.

## Routes

### Foundation route

`/` is a public GET/HEAD route rendering `home.html`, with no input and no writes. Other methods return 405; unresolved paths and uncaught exceptions use generic nondebug 404/500 responses, the 404 rendering `404.html` from ACC-2. Its observable contract is [PLT-1](product/platform.md#plt-1-django-foundation-and-continuous-verification); from ACC-1 the page also links to `/sign-in/` (PLT-1.1). From ACC-2 it reads the session to redirect a signed-in user to their role home, and its button's form carries Django's CSRF token, which sets the CSRF cookie; the view stays CSRF-exempt so other methods keep PLT-1.2's 405. Future routes must define authorization, validation and state contracts before implementation.

The accounts and rounds routes below are planned for their implementation slices; ACC-2 turns `/` into the accounts start page in the table below. Each route contract must name its method, role/workspace/ownership checks, input validation, state preconditions, success result and denied/failure behaviour before implementation.

### Accounts routes

For [ACC](product/accounts.md). Every POST uses Django's CSRF protection, which also rejects an `Origin` header naming another origin, with 403 ([ACC-1.8](product/accounts.md#acc-1-sign-in-and-out-by-role), [ACC-2.7](product/accounts.md#acc-2-create-an-isolated-demo-workspace)). A storage failure in demo creation, or in sign-in from its pre-check through its [limited transaction](#accounts-and-workspaces), authentication included, gives the 503 page of [ACC-2.5](product/accounts.md#acc-2-create-an-isolated-demo-workspace) and changes nothing; other storage failures on these routes, including starting the session after a successful sign-in, give the generic 500 of PLT-1.3, except a failed save of an existing session row at the end of a request, which follows the [persistence decision](#data-model). Signing out a signed-in user deletes the old session row and then creates a new one for its message, so a failure to create it leaves the session ended with the generic 500.

## Configuration

The `.env.example` file may contain only empty placeholders and throwaway local database values. Only `relay.settings.local` loads the optional repository-root `.env` using a small standard-library loader, before reading configuration; its path is fixed relative to the settings source, independent of the current working directory. Test and production settings never load dotenv files. Local settings read `DJANGO_SECRET_KEY` (required/nonblank), `DJANGO_DEBUG` (strict true/false; defaults false), `DJANGO_ALLOWED_HOSTS` (comma-separated localhost/127.0.0.1/[::1] only), and `POSTGRES_HOST/PORT/DB/USER/PASSWORD` (defaults localhost/5432/relay/relay/relay). Database host must be localhost, 127.0.0.1 or ::1. These local settings cannot configure a hosted runtime. `manage.py` and WSGI default to local settings; explicit `DJANGO_SETTINGS_MODULE` remains supported. The WSGI entrypoint makes its file-relative `src` package root importable before Django initialization, including when a host loads the entrypoint directly by file path without `PYTHONPATH`.

- Dotenv loading is limited to the existing local names above and `SOC_LLM_ENDPOINT`, `SOC_LLM_MODEL`, `SOC_LLM_API_KEY`. Unknown names are ignored, including `DJANGO_SETTINGS_MODULE`, `SOC_LLM_LIVE`, production-only names and interpreter/process options. The loader fills only absent process-environment keys; an existing value, including an empty string, wins. For repeated allowed names within the file, the last assignment supplies the file value.
- Supported UTF-8 syntax is one `KEY=value` assignment per line with surrounding whitespace removed, optional `export` before the key, blank lines and whole-line `#` comments. Matching single or double outer quotes delimit a literal single-line value and are removed. There is no shell execution, variable interpolation, escape decoding, multiline syntax or inline-comment processing; `#` within a value is literal. Malformed assignments/quoting for recognized names reject startup; unknown-name lines do not configure anything. A missing file is optional; other read/decoding failures reject startup. Loader errors use a fixed `ImproperlyConfigured` message with no file content, value or chained underlying exception. Existing local value validations still apply after loading.
- Configuration tests use synthetic temporary files only. Before introducing local auto-loading, subprocess settings/database/isolated-WSGI probes must substitute the loader's path in Python before importing local settings; no environment-controlled runtime path override is added. Probes must never read or print the developer's real dotenv contents, including during negative tests or direct-file startup without `PYTHONPATH`.

`relay.settings.test` imports only shared settings and uses fixed non-secret values: PostgreSQL database/user/password `relay_test`, host 127.0.0.1, port 55432, test database `test_relay_test`, debug false and hosts testserver/localhost/127.0.0.1. `pytest.ini` selects these settings; tests use no provider. An autouse fixture in `src/conftest.py` removes every `SOC_LLM_*` environment variable and makes the gateway transport's network step fail, unless a test is marked `llm_transport`; those tests use only a local server. The test role needs database creation permission on its throwaway server. ACC-1 adds the first business migrations.

The gateway makes no provider call while its [live switch](ai/llm-gateway.md#live-switch) is off. When it is on, the gateway reads `SOC_LLM_ENDPOINT`, `SOC_LLM_MODEL` and `SOC_LLM_API_KEY` from the environment at each call; a missing or invalid value is a refusal. `.env.example` lists them empty.

Both database configurations explicitly set libpq `hostaddr` through Django's database `OPTIONS`, preventing inherited `PGHOSTADDR` from redirecting connections. Local localhost/127.0.0.1 map to 127.0.0.1; local ::1 maps to ::1. Tests fix the address to 127.0.0.1.

In every environment, the shared settings install Django's `XFrameOptionsMiddleware` first, above `SecurityMiddleware`, so every response Django makes refuses framing (`X-Frame-Options: DENY`): pages, error pages, and responses other middleware makes, such as an HTTPS redirect, the 400 for a disallowed host or a failed session save, and the 500 when a new session row cannot be created. No view is exempt, and no code sets the header or `X_FRAME_OPTIONS` itself, so Django's default `DENY` applies (#58). Responses served outside Django, such as the platform's own error pages, are not covered.

Production settings, checked before release:

- Explicitly select `relay.settings.production` with `DJANGO_SETTINGS_MODULE`; local and WSGI defaults stay local. Production requires a nonblank `DJANGO_SECRET_KEY`, one DNS hostname in `DJANGO_PRODUCTION_HOST` and `DATABASE_URL`. Reject a host containing a scheme, path, port, wildcard or loopback name/address. Set `DEBUG=False`, `ALLOWED_HOSTS` to that host and `CSRF_TRUSTED_ORIGINS` to its HTTPS origin; inherited local debug/host variables cannot override them. Configuration errors identify only the invalid variable, never its value.
- `DATABASE_URL` is a PostgreSQL URL with an explicit database, user, password and hosted DNS endpoint. Use Neon's pooled endpoint for Vercel requests and the direct endpoint for the migration job. Require certificate-verified TLS (`sslmode=verify-full`, system root certificates), a 10-second connection timeout, `CONN_MAX_AGE=0` and `DISABLE_SERVER_SIDE_CURSORS=True`; do not accept URL query options that weaken or override this policy. Settings do not read dotenv files. Operators keep unrelated libpq overrides out of the hosted environment.
- `DJANGO_TRUST_PROXY_SSL_HEADER` accepts only `true` or `false`, defaulting to false. Only after Vercel's actual `X-Forwarded-Proto` behavior is observed under the [release gate](#release-verification) may the operator set it true, enabling `SECURE_PROXY_SSL_HEADER=('HTTP_X_FORWARDED_PROTO', 'https')` and Django's HTTPS redirect. The protected bootstrap may leave it false while gathering observations; it does not establish production HTTPS detection or pass final deployment checks. Public delivery requires true.
- HSTS is enabled for one year, without preload or extending to other subdomains. Silence only Django's deployment warnings recommending those two optional HSTS expansions; do not silence other deployment warnings. Session and CSRF cookies retain the shared Secure settings.
- Production keeps the shared middleware, with `XFrameOptionsMiddleware` first, and its responses carry `X-Frame-Options: DENY`.

The Vercel project uses the repository root, native Django detection of `src/manage.py` and `relay.wsgi.application`, Python 3.14 and a 60-second function limit on `src/relay/wsgi.py`. The project is unlinked from Git; `vercel.json` also disables automatic Git deployments. The protected delivery job installs Vercel CLI `64.3.1` on Node `24.18.0` before receiving production secrets and uploads prepared source. Hosting introduces no additional Python runtime dependency, staging service or application container.
