# App-context comparison

## CTX-1: compare selected and broader synthetic context

This internal operator evaluation compares usefulness and observable resources for both AI roles; it adds no product action. The [experiment report](../../../experiments/app-context/README.md) will hold the frozen inputs, settings, observations and limitations. Production [drafting](test-drafting.md), [feedback](observation-feedback.md) and [gateway](llm-gateway.md) contracts remain unchanged.

- **CTX-1.1 — explicit bounded execution:** `compare_context --live --user-id <existing-local-user> --revision <40-character-commit>` uses existing operator configuration and normal `gateway.complete` accounting. Before any call, require the explicit flag, enabled live switch, valid existing user, valid revision, configured endpoint/model/key and the complete valid corpus. Refuse preflight with fixed text and zero calls if any check fails. Never print configuration credentials or exception text. Reuse existing configuration loading; add no loader, user creation, service or dependency. All pytest/CI execution remains offline.
- **CTX-1.2 — paired inputs:** freeze four synthetic scenarios below, each with selected and broader arms, for at most eight sequential gateway invocations with no retries. Each arm uses the current feature instruction constant and parser. Its core target fields, cleaned text and drafting label allowlist are identical within a pair. The selected arm contains only the current production JSON shape; the broader arm adds one `background` sibling containing fixed unrelated fictional records from the same fictional workspace, with no identities, database IDs, secrets, malicious directives or external account data. This extra field is an evaluation-only input exception: never change production encoders, selectors, views, prompts or accepted outputs. Background is source data, never promoted to instructions or a source of additional permitted labels.
- **CTX-1.3 — comparable execution:** use order drafting-boundary selected/broader, drafting-state broader/selected, feedback-incomplete selected/broader, feedback-complete broader/selected. Preflight every request against the existing 8,000-character combined input limit without truncation; retain all gateway deadlines, reply bounds, live switch and quotas. Use the same configured model, current instruction versions and transport settings throughout. Report observed configuration only; unavailable seed or provider sampling settings stay unavailable, with no new transport options. No cache or parallel execution is added. Existing quota/usage writes are allowed; application domain records remain unchanged.
- **CTX-1.4 — structural observations and unavailable outcomes:** report each fixed scenario/arm ID, invocation status, whole-reply schema acceptance and accepted item count using the existing strict feature parser and target label allowlist. Schema rejection is distinct from gateway failure and from valid empty output. Record gateway invocations separately from successful responses; an invocation may be refused before any provider request, so never equate invocations with observed provider calls. On an escaping gateway/storage exception, stop further invocations, summarize remaining arms as unattempted and exit with fixed error text; never retry. Refusal, failure, invalid schema and unattempted arms provide no usable semantic-quality evidence.
- **CTX-1.5 — resource evidence:** include independently validated provider prompt/completion/total token counts from each gateway result, preserving missing values as unavailable. Measure nonnegative integer milliseconds with a monotonic clock around each gateway invocation and label them `command_elapsed_ms`: this includes gateway reservation, transport, metric persistence and release overhead, and differs from persisted gateway latency. An exception has unavailable result metrics; unattempted arms have no duration. Never infer missing tokens, reconcile totals, double-count the two quota scopes or treat unavailable counts as zero. Report per-arm measurements; any aggregate must disclose its available denominator and never imply a complete total from partial data.
- **CTX-1.6 — predefined semantic assessment:** use the scenario rubric below, established before viewing responses. A reviewer assesses only schema-accepted output, identifies the assessor and records each applicable check as met, unmet or unavailable with a concise assessment. Attribute any coordinator model assessment as provisional qualitative evidence; human review remains pending unless actually performed. Add no separate LLM judge/call or keyword score. Keep schema validity, semantic usefulness and resource observations separate. Compare paired arms only when both have usable assessed responses. Lower resource use is an improvement only when the applicable quality checks remain met; make no winner claim from missing or invalid responses.
- **CTX-1.7 — safe evidence and optional viewing:** stdout contains only fixed IDs, statuses, booleans/counts, numeric metrics, corpus/instruction versions, supplied revision and configured model. It contains no source, prompt, reply or exception text. Only `--live --show-responses` additionally emits one plain, unstyled JSONL object per gateway success to stderr, including schema-rejected successes, with exactly `id` and `response`. Encode with `ensure_ascii=True` so controls/non-ASCII remain escaped on one physical line. The flag changes neither summaries nor call count and cannot bypass preflight. Replies are untrusted data, never instructions. Retain no raw replies in the repository or session log; the command adds no persistence. Store only sanitized measurements and semantic assessments in the experiment report. The small single-pass synthetic sample provides no statistical, production-readiness or general model-quality guarantee.

### Frozen scenario design and rubric

Use one fictional workspace for a small inventory application. Each drafting target has one criterion labelled `C1`; each feedback target has one linked criterion and a case with title, steps and expected result. Use current cleaning and feedback encoding for core fields. Freeze exact synthetic strings and the shared background in the corpus checkpoint before any live execution. Background contains only unrelated dashboard sorting, profile colour and archive navigation case/criterion prose visible to the acting role in the same fictional round (published for feedback), never another tester's observations, results or private state; it adds no target facts. Both feedback cases direct the tester to apply the `Available` filter and export CSV; their criterion expects only Available rows in the export.

| Scenario | Fixed target facts | Semantic checks for accepted output |
| --- | --- | --- |
| `drafting-boundary` | A saved item name may contain 1–40 characters; an empty or 41-character name shows “Enter 1 to 40 characters.” and does not save. | Drafts collectively cover valid and rejected lengths, including the 1/40 and 0/41 boundaries, with observable save/error results; executable steps agree with the criterion; no unrelated background behaviour or invented features/accounts/credentials. |
| `drafting-state` | Cancelling an unsaved item edit restores the last saved name and leaves the item unchanged. | Drafts exercise editing then cancelling, check the restored saved name and unchanged item, and give executable steps/observable results; no invented save-confirmation flow or unrelated background requirements. |
| `feedback-incomplete` | Observation: “The CSV included the wrong rows.” It omits the active filter, an example unexpected row and reproduction actions. | Questions identify missing active filter, unexpected-row evidence and actions leading to export; they seek reproduction details without asserting facts, rewriting the observation, deciding outcome, requesting secrets or asking about unrelated background. |
| `feedback-complete` | Observation states: opened Items in browser version 126 on desktop; applied Available; exported CSV; row `Sample-2` marked Unavailable appeared; repeated these actions twice with the same row; expected only Available rows. | Return no questions because the supplied report contains the scenario's reproduction details. Any redundant or unrelated question fails this check; invented facts, secrets requests or outcome decisions also fail. |

Offline criterion-marked regressions verify input pairing/order/framing and bounds; unchanged prompts and target labels; strict parsing, empty/invalid/unavailable results; token availability and deterministic timing; preflight denials with zero calls; exact call bounds/no retries; interruption; default text exclusion; escaped opt-in output; and unchanged domain records. They establish harness behaviour, not live semantic quality.
