# Shared LLM gateway

Relay's one boundary for SoC LLM calls, using the [configured operator environment](#live-switch).

The chat-completions adapter, runtime safety controls and shared code-level live switch are built. A real provider smoke check and drafting evaluation remain pending; local tests do not establish provider availability or production readiness.

The chat format below adapts the MP3 implementation at commit `97ad991` (`src/deskmate/llm.py` and `src/deskmate/llm_gateway.py`): endpoint `https://soclaas-api.comp.nus.edu.sg/v1/chat/completions`, model `llama3.1:8b`, Bearer authentication and `choices[0].message.content`. This is local implementation evidence, not confirmation of current availability, limits or provider terms; endpoint and model remain configured values. The [integration plan](../../plans/6-soc-chat-completions.md) tracks this change separately from the frozen original gateway plan.

On 2026-10-31 the human confirmed no provider retention, no use for training and current provider defaults of 90 requests/minute, 80,000,000 microdollars ($80)/day and 800,000,000 microdollars ($800)/month. These are human-supplied confirmations, not independently reverified provider terms. Relay's application caps below remain unchanged.

## Responsibilities

Feature code authorizes the user and selects source records before invoking the gateway. The gateway keeps fixed developer instructions apart from source data, bounds requests and replies, and returns exactly one of `Success(text)`, `Refused(code)` or `Failed(code)`. Features validate their own structured reply; the gateway checks only the outer envelope. Checked output remains untrusted.

The [security spec](../SECURITY-SPEC.md#ai-features-and-prompt-injection) owns threats and controls; feature contracts own their exact inputs, instructions and accepted outputs.

## Live switch

- `SOC_LLM_LIVE=True` in the shared settings (`relay.settings.base`) is a code-level setting, not read from the environment. Fixed test settings override it to `False`; operators must configure the endpoint, model and key before invoking the provider. Missing or invalid settings refuse without a network call.
- While it is off, `gateway.complete` called without a test provider returns `Refused("live-off")` before any quota record, reservation or transport step, and the transport also refuses before reading any `SOC_LLM_*` variable. No network call is made, whatever `SOC_LLM_*` holds.
- The MP3 format evidence and human confirmations above support this integration; a live smoke check and the feature's live evaluation remain separate manual validation, never inferred from fake-provider or local transport tests.
- `ssl.create_default_context()` honours `SSLKEYLOGFILE`, `SSL_CERT_FILE` and `SSL_CERT_DIR`. The transport clears each fresh context's `keylog_filename` before use to prevent TLS key logging. `SSL_CERT_FILE` and `SSL_CERT_DIR`, if set, must name only trusted CA stores; that remains an operator environment obligation.
- Each call's event loop explicitly disables asyncio debug mode, including when `PYTHONASYNCIODEBUG` or `-X dev` would enable it, to prevent raw asyncio debug reports from bypassing the fixed-code handler. Production debug mode must still remain off.
- The transport connects directly and ignores `HTTPS_PROXY` and the other proxy variables. Operators must confirm direct provider reachability in the deployment environment; this integration adds no proxy support.
- RND-8's [notice](../product/rounds.md#rnd-8-draft-test-cases-with-ai) says what is sent. Its drafting UI is built; real provider smoke checks and live evaluation remain pending.

## Transport contract (proposed)

The rules below are implemented; the historical "proposed" headings remain for existing links. Relay owns these rules; the [aiohttp](https://docs.aiohttp.org/) client library does the networking: name resolution, connecting, TLS, HTTP parsing and knowing when a response is complete.

- One fixed HTTPS endpoint from `SOC_LLM_ENDPOINT`, with no credentials or fragment in the URL. The request is one `POST` with the JSON body below. The system message contains only the feature's fixed instructions; the user message contains the feature's source JSON text unchanged as a string, never promoted into instructions or parsed into additional messages. No tool, browsing or function-calling fields are sent. No `max_tokens` value is introduced: MP3's 512-token setting does not establish a suitable cap for Relay's drafting reply. Existing local reply, byte and time bounds still apply. Certificate and hostname verification are on, using a verifying context made for each call; no redirect is followed (a 3xx is `Failed("transport")`); and no proxy is used ([live switch](#live-switch)). No call retries.

  ```json
  {"model": "<SOC_LLM_MODEL>", "messages": [{"role": "system", "content": "<fixed instructions>"}, {"role": "user", "content": "<source JSON text>"}], "temperature": 0, "stream": false}
  ```

- `SOC_LLM_API_KEY` goes in the `Authorization: Bearer` header and is never placed in the body, logs or an error message. The transport and `complete` mark the key, headers, body, instructions and data as Django sensitive variables.
- **Deadline.** One 30-second deadline starts when the call's slots are reserved, at the moment taken after the slot locks are acquired. The time left at the start of the request is aiohttp's total timeout for the whole request, reading the body included; aiohttp may round it up by under a second, within the release margin. The call runs on its own event loop, which is closed without waiting for a name lookup still running, so a hung lookup does not extend the call. A complete response returns without waiting for the server to close the connection.
- **After the call.** Whatever the outcome (a reply, an error, a timeout or an oversized body), before the transport returns, the call's remaining tasks are cancelled and given at most 1 second to finish, and its asynchronous generators are then closed within whatever time of that same second is left; a task or generator that ignores cancellation is abandoned, not awaited. Then every transport the call's loop opened is aborted without a TLS close exchange, each separately so one failing abort, logged only as the fixed code `abort-failed`, skips none of the others, any socket of those connections still open is closed, and the loop is closed; a socket still connecting or in the TLS handshake is closed when the timeout cancels that step. With aiohttp's rounding, the call still ends within the release margin. asyncio's reports through the call loop's exception handler are logged only as one of the fixed codes `leftover-task`, `asyncgen-close`, `connection-error` and `loop-error`, chosen from which kind of object the report names, never with message, exception or task text; asyncio's own debug-mode logging (`PYTHONASYNCIODEBUG` or `-X dev`) bypasses that handler and can log connection and operating-system details, so debug mode must stay off in production. Each name lookup runs `getaddrinfo` in its own daemon thread, so a hung lookup delays neither the call nor interpreter exit, such as a worker's shutdown. A thread blocked in the operating system's resolver cannot be stopped: it keeps running, holding no socket of Relay's, until the resolver returns or times out. Each counted call can leave at most one such thread, so at most 20 per user and 200 per deployment can be started in any rolling hour; the in-flight caps do not bound them, because the call's slots are released while the thread still runs. They accumulate only while the resolver fails to return. Cancellable lookups would need an asynchronous resolver such as aiodns, a dependency not adopted.
- The request asks for an uncompressed reply, and the response body is capped at 244,096 bytes as received, without decompression (12 bytes for each of 20,000 reply characters, the longest JSON escape of one character, plus 4,096); a longer body is `Failed("invalid-response")`. aiohttp's own limits bound the status line and headers.
- A 2xx response body must be one JSON object with a nonempty `choices` array. Read only its first choice, which must be an object containing a `message` object. Normal provider metadata (for example `id`, `model`, `usage` and `index`) and later choices are ignored, never passed to a feature or stored; the first choice's `finish_reason` is checked only for the refusal/truncation cases below. If present, `message.role` must be `assistant`. Non-null `tool_calls` or `function_call` in that message are invalid; no tool result is accepted as text.
- For success, `message.content` must be a string of at most 20,000 characters with no surrogate code point; an empty string is allowed at the gateway boundary and remains subject to feature validation. An absent or null `message.refusal` permits success. A nonempty string `message.refusal` is `Refused("provider-refused")` even if content is also present; an empty or non-string refusal is invalid. A first choice with `finish_reason` equal to `content_filter` is also `Refused("provider-refused")`; `length` without a refusal is `Failed("invalid-response")`, because its content is truncated. Missing/null/non-string content without a refusal is invalid. Legacy top-level `text` or `refusal` objects are no longer accepted.
- Invalid UTF-8, repeated keys anywhere (including ignored metadata), `NaN`, `Infinity`, `-Infinity`, parser recursion failure (`RecursionError`) and any other JSON parse error are `Failed("invalid-response")`. No independent numeric nesting limit is imposed; the existing response byte cap bounds all envelope metadata. Every other envelope violation above has the same result. The character/surrogate rule applies to accepted content; ignored metadata is not interpreted as feature text.
- HTTP 400, 401 and 403 and the chat refusals above are `Refused("provider-refused")`; 429 is `Refused("quota")`; a missing or invalid setting is `Refused("not-configured")`; 3xx, 5xx and other non-2xx statuses are `Failed("transport")`. Exceptions map to fixed codes, timeouts first: the total timeout is `Failed("timeout")`; an aiohttp client error (connection, TLS, malformed HTTP or an incomplete body), `OSError`, `ValueError` (such as a host name that cannot be encoded) or any other `Exception` is `Failed("transport")`; cancellation and interpreter-exit exceptions (`BaseException`) propagate after the slots are released. Provider bodies and exception text never reach the feature or logs.
- The gateway logs only the fixed outcome code, never instructions, data, reply text or exception text.

## Limits and accounting (proposed)

- A request whose instructions plus data exceed 8,000 characters is `Refused("input-too-large")` before any reservation.
- Each user has at most 1 call in flight and the deployment at most 2. Quota is 20 calls per user per rolling hour and 200 per deployment per rolling hour. One transaction locks the call slots, checks both quotas and records the call before the call starts, so failed, refused and timed-out calls count; any refusal is `Refused("busy-or-quota")`.
- `ai.CallSlot` rows hold the reservations ([data model](../TECHNICAL-SPEC.md#ai-gateway)). A reservation sets the user's slot and one free deployment slot to expire 35 seconds after it is made, the same moment the deadline starts: the 30-second deadline plus a 5-second margin for releasing. Release runs on every exit and only clears a slot that still holds this call's expiry, so a call that ends late cannot clear a later call's reservation. An expired slot is free.
- `ai.CallRecord` keeps one timestamp per counted call. Records older than their window are deleted while that quota's lock is held.
- A storage error while reserving or releasing is raised to the feature, which applies its own storage-failure rule instead of reporting the AI service as unavailable.
- The gateway stores no prompt, source or reply text and records no token metrics. A later slice that records them stores a missing provider value as unavailable, never zero.
- There is no result cache. A future feature that adds one must isolate it by access scope and source version.

## Fake provider and verification

`ai.fakes.FakeProvider` is scriptable with an exact reply, refusal, failure or timeout and records the instructions and data it was given. Tests pass it to `complete` instead of using the transport; the live switch does not apply to it. The [test configuration](../TECHNICAL-SPEC.md#configuration) keeps every other test away from the transport and the network.

The test seam does not bypass the shared result boundary: `Success.text` must satisfy the transport's content type, character and surrogate rules, otherwise it becomes `Failed("invalid-response")`. `Refused.code` and `Failed.code` must be strings from their respective fixed gateway outcomes above (also `Failed("provider-error")` for a test-provider exception or malformed result); an unknown code or malformed result becomes `Failed("provider-error")` before returning or logging. No provider-supplied text becomes an outcome code.

The live check is an operator step, not CI, and needs the live switch on: configure the endpoint, model and key, run the drafting [live evaluation](test-drafting.md#live-evaluation), and record results in a log.
