# Platform

Platform area `PLT`; see the [product spec](../PRODUCT-SPEC.md).

## PLT-1: Django foundation and continuous verification

- **PLT-1.1:** A signed-out visitor can GET `/` without an account and receive an HTML page titled `Relay`, headed `Relay`, with the text `A beta-testing portal for small software teams.` and `Testing workflows are coming soon.` A HEAD request succeeds with an empty body. The page has a "Sign in" link to `/sign-in/` and a "Create a demo workspace" button that POSTs to `/demo/`, and no other links, forms or actions. A signed-in user is redirected to their own role home ([ACC-2.6](accounts.md#acc-2-create-an-isolated-demo-workspace)).
- **PLT-1.2:** `/` accepts only GET and HEAD. Other HTTP methods return 405 and advertise GET and HEAD; requests do not create application state.
- **PLT-1.3:** With debug disabled, unknown routes return a generic 404 and unexpected server failures return a generic 500, without reflecting request data, exception details or source paths.
- **PLT-1.4:** Local startup uses explicit local settings, requires a nonblank secret key from the process environment or optional repository-root dotenv configuration, permits only loopback hosts/database connections, and rejects malformed configuration without disclosing dotenv values. Existing process values, including empty ones, override file values; local dotenv syntax and allowed names follow the [configuration contract](../TECHNICAL-SPEC.md#configuration). Production startup selects separate production settings explicitly; it does not relax local restrictions or load dotenv files.
- **PLT-1.5:** Automated tests select fixed test-only settings, with debug disabled and a separate PostgreSQL database, ignoring inherited runtime secrets, debug, hosts, database and provider variables. Test settings never read dotenv files or call an AI provider; local-configuration probes isolate dotenv loading to synthetic temporary paths.
- **PLT-1.6:** Database tests can create an isolated PostgreSQL test database, write/read synthetic data, and roll back test writes without changing the normal local database.
- **PLT-1.7:** Pull requests and pushes to `main` run lint, formatting, Django system checks and the complete pytest suite in the existing `verify` CI job against throwaway PostgreSQL, with pinned actions, read-only repository access and no stored secrets or deployment.
- **PLT-1.8:** Production startup rejects missing or malformed required configuration without printing its values. Debug stays off; only the configured production host and HTTPS origin are allowed, cookies are Secure, framing is denied, and HSTS is enabled. Database connections require TLS and use the production connection policy in the [technical spec](../TECHNICAL-SPEC.md#configuration); production settings do not load dotenv files or change fixed test settings.
- **PLT-1.9:** Application delivery is disabled unless an operator explicitly enables it after the initial release gate. Thereafter an approved pull request merged to `main` triggers automatic delivery after successful application and site verification in that same push workflow run, without another environment approval or manual trigger. Only pushes to `main` can enter the production job; pull request runs, failed or skipped prerequisites and an unset or false opt-in cannot deploy. Production credentials are confined to that main-restricted environment job; validation receives none. Production deliveries are serialized without cancelling a running delivery.
- **PLT-1.10:** The production job checks out its workflow run's exact tested commit and prepares a fresh deployment archive from only that commit's application/build inputs. Missing required inputs, unsafe archive entries or preparation failure prevent upload. Dotenv files, Git metadata and local/uncommitted artifacts are excluded. A pinned Vercel CLI uploads that prepared source to the configured unlinked project. Source assurance comes from the tested commit and controlled archive preparation, not caller-supplied commit metadata or independent provider source-content verification; no moving branch is used for source retrieval.
- **PLT-1.11:** Production configuration checks and migrations against the direct database endpoint finish successfully before a Vercel deployment is requested. Their failure prevents that request. The checked commit's migrations must remain compatible with the currently serving application; previously committed migrations are not automatically reversed if a later stage fails.
- **PLT-1.12:** A delivery succeeds only after the source archive is uploaded, the resulting deployment is ready in the configured production project, its production hostname points to that deployment and the smoke checks pass. Archive, CLI or API failure, missing/mismatched deployment identity, terminal failure, deadline expiry or smoke failure fails the job. Reports identify the tested commit, known deployment ID and failed stage without printing credentials, raw CLI output, request/response bodies or application content. The workflow/helper invokes deployment creation once and does not rerun the CLI after a failed, timed-out or ambiguous invocation; an operator inspects the outcome before deciding the next action. This does not claim that the vendor CLI performs no internal protocol retries.
- **PLT-1.13:** After readiness, bounded anonymous HTTPS requests to the configured production origin check the start page, sign-in page and a missing route, their expected statuses and fixed text, and the required security headers. Redirects, unexpected content/status/header values and request timeout fail the smoke check. Smoke checks create no accounts or application records, submit no forms and use no production user credentials.
- **PLT-1.14 [manual]:** Before initially enabling public production delivery, an authorized operator completes and records the existing [release gate](../TECHNICAL-SPEC.md#release-verification), configures hosted production restrictions and explicitly approves initial public activation. This one-time gate does not require a separate approval for each later approved merge. An initially protected deployment of a verified commit may collect these observations in the same project/database; it is not a public release. Failed observations leave public delivery disabled. Record the hosted commit, URL and actual results separately from automated evidence. This is manual because local tests cannot establish the provider's actual proxy behavior, protection settings, database limits or human approval.

## PLT-2: Validate and publish the product website

- **PLT-2.1:** The public static landing page identifies Relay as a beta-testing portal, explains the Test Coordinator and Beta Tester roles, and distinguishes built behaviour from planned work. It links to the team's repository, the source User Guide and Developer Guide, and the rendered Reflections page; it does not present an unverified hosted Django application as available.
- **PLT-2.2:** The rendered site includes the landing page, Reflections page and theme assets beneath the configured repository base path. Local page and asset links resolve within the rendered artifact. The User Guide and Developer Guide remain repository-source links and are excluded from the published artifact.
- **PLT-2.3:** Pull requests and pushes to `main` build and check the static site without stored secrets or publication privileges. A build or rendered-artifact validation failure fails that site check and prevents its artifact from being offered for publication.
- **PLT-2.4:** Only a push to `main` can publish the checked site artifact, after both the application `verify` job and site validation in that same workflow run succeed. Pull requests cannot publish; failed or skipped prerequisites prevent publication. A failed publication is reported as failure, never as a successful release.
- **PLT-2.5:** Publication permissions are confined to the Pages deployment job, which uses the `github-pages` environment and publishes the artifact from its own workflow run. Validation retains read-only repository access; the existing Django verification and application behaviour are preserved.
- **PLT-2.6:** After operator-authorized Pages setup and release, an anonymous visitor can open the configured HTTPS site and follow its landing-page, Reflections and theme-asset links. Record the deployed commit, URL and actual results separately from build evidence. Hosted verification remains pending until setup and release; a passing build alone does not meet it.

## PLT-3: Record LLM usage and latency

- **PLT-3.1:** Every successfully reserved gateway call retains its existing quota records and records the same elapsed milliseconds and available provider token counts on both scope rows when the call returns a gateway result. These rows represent one call, not two; readings use one scope only. Existing rows and unfinished calls have unavailable metrics.
- **PLT-3.2:** Provider-reported prompt, completion and total token counts are validated independently under the [gateway accounting contract](../ai/llm-gateway.md#usage-and-latency). A reported zero stays zero; absent, null, malformed or out-of-range values remain unavailable, with no estimation or inferred total. Optional usage cannot change a valid reply or refusal into a failure.
- **PLT-3.3:** Elapsed time uses a monotonic clock from the existing reservation moment until a checked gateway result is available, excluding metric persistence and slot release. Success, provider refusal, invalid response, transport failure, timeout and test-provider failure record latency even when usage is unavailable.
- **PLT-3.4:** Live-off, oversized-input and busy/quota refusals before successful reservation create no call records or metrics and do not invoke the provider. Refusals after reservation retain the existing quota charge and record latency. Usage recording preserves existing outcomes, quotas, deadlines, cleanup and transport controls.
- **PLT-3.5:** A metrics storage failure propagates as a storage error to the feature, with no provider retry and no success returned; neither scope row receives a partial metrics update. Slot release is still attempted. Reservation and release storage errors retain their existing feature handling.
- **PLT-3.6:** Persist only numeric usage and latency on the existing records, with no prompt, source, reply, credentials or raw metadata in records or logs. Existing lazy quota cleanup governs these metrics; inactive users' old rows remain until their next call. There is no new viewer, export, service or cleanup subsystem.

## PLT-4: Shared application presentation

The existing Django start, sign-in, demo credentials, coordinator, tester and AI pages share this presentation. Their existing copy, actions, permissions, workflows and user-text escaping/direction isolation remain governed by their existing requirements.

- **PLT-4.1:** Pages show a pale grey-blue background surrounding a distinct white content surface. At wide desktop sizes the surface is centered and bounded in width; headings, paragraphs, lists and sections have consistent spacing and a readable system-font hierarchy, with body text at least 16 CSS pixels.
- **PLT-4.2:** Existing links are visibly identifiable, buttons share a consistent appearance, and text inputs, password inputs, textareas, selects and checkbox groups have readable labels and consistent spacing. Text-entry controls fit their available width; checkbox labels remain beside their choices. Styling preserves each control's native operation.
- **PLT-4.3:** Existing status messages and validation/action errors have distinct, consistent visual treatments while retaining their exact text. The demo credentials table has clear headers, cell spacing and row separation, and every credential remains readable and selectable.
- **PLT-4.4:** At 320 CSS pixels and at a wide desktop viewport, the pages have no horizontal page overflow or clipped controls. Long unbroken user-authored text and demo credentials wrap within the content surface without hiding text or changing its escaping and direction isolation. Forms, tables and AI suggestions remain readable in a single-column document flow.
- **PLT-4.5:** Keyboard navigation gives links, buttons and form controls a clearly visible focus outline without clipping it. Shared text and link colors contrast with their backgrounds by at least 4.5:1; button labels meet the same ratio, and focus outlines contrast with the adjacent surface by at least 3:1. Links and status/error text remain understandable without relying on color alone.
