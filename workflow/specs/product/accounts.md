# Accounts

Planning area `ACC`. ACC-1 to ACC-5 are implemented, including ACC-2's sample draft round from RND-7. See the [roles](../PRODUCT-SPEC.md#roles); storage and routes are in the [technical spec](../TECHNICAL-SPEC.md#accounts-and-workspaces), and controls in the [security spec](../SECURITY-SPEC.md#sign-in-and-access-control).

Every account belongs to exactly one workspace and has exactly one role, Test Coordinator or Beta Tester. Accounts originate in demo workspace creation (ACC-2), with additional Beta Testers defined by ACC-4 and coordinator-managed tester password reset defined by ACC-5. Self-registration, coordinator account recovery, self-service password reset, invitations, editing or removing accounts, email, MFA and SSO are not part of Relay.

Each criterion is labelled happy, boundary, failure, adversarial or ambiguous.

## ACC-1 Sign in and out by role

A user signs in with a username and password and works on their own role's home page: "Coordinator home" for a Test Coordinator, "Tester home" for a Beta Tester. A home page shows the user's username and workspace name. The Relay start page, at `/`, is separate from both.

- **ACC-1.1** (happy) Signing in with a valid username and password opens the user's own role home page, whatever `next` value or other redirect target the request carries.
- **ACC-1.2** (failure) A wrong password, an unknown username or a blank field shows the sign-in page again with "Username or password is incorrect." The response does not reveal which field was wrong. A signed-out visitor stays signed out, and a signed-in user's existing session is unchanged, except that any unread message it held is shown on that page.
- **ACC-1.3** (failure) A signed-out visitor requesting a role home page is redirected to the sign-in page.
- **ACC-1.4** (adversarial) A signed-in user requesting the other role's home page gets a 403 page saying "You do not have access to this page." It shows no workspace data, and the user stays signed in.
- **ACC-1.5** (happy) Signing out ends the session on the server and shows the sign-in page with "You have signed out." Requesting a role home page afterwards, even with the old session cookie, redirects to the sign-in page. A signed-out visitor who signs out gets the sign-in page with no message. A GET request to the sign-out route does not sign out.
- **ACC-1.6** (boundary) A session ends 8 hours after sign-in, whatever the activity, including requests that change the session in between. Just before that time a role home page opens; at or after it, the request is redirected to the sign-in page.
- **ACC-1.7** (adversarial) Every successful sign-in, whether the visitor was signed out or signed in as anyone, starts a session with a new identifier. Any identifier held before that sign-in no longer authenticates.
- **ACC-1.8** (adversarial) A sign-in or sign-out request without a valid CSRF token, or whose `Origin` header names another origin, is refused with 403 and changes nothing.

## ACC-2 Create an isolated demo workspace

A signed-out visitor can choose "Create a demo workspace" on the Relay start page to get a fresh workspace for trying both roles. The workspace also contains a sample draft round, which is RND-7 in [rounds](rounds.md).

The "Your demo workspace" page, titled and headed "Your demo workspace", shows "Workspace: <workspace name>", then a table with the columns "Role", "Username" and "Password" and one row per account: the Test Coordinator first, then the two Beta Testers. Below it are "Save these passwords now. They will not be shown again." and a "Sign in" link to the sign-in page. The 503 page and the 404 page show their message as their only heading, after the [home link](platform.md#plt-4-shared-application-presentation) of PLT-4.17.

- **ACC-2.1** (happy) Creating a demo workspace shows a "Your demo workspace" page listing the workspace name and, for each account, its role, username and password, with "Save these passwords now. They will not be shown again." The visitor stays signed out.
- **ACC-2.2** (boundary) The workspace has exactly 1 Test Coordinator and 2 Beta Testers. Each listed username and password signs in to that account's role home page, which shows the new workspace's name.
- **ACC-2.3** (adversarial) Passwords are stored only as password hashes. No GET page, later response, log entry or database field shows a generated password again, and the creation response tells the browser not to cache it.
- **ACC-2.4** (adversarial) Two workspaces share no accounts, and a user's pages show only their own workspace. Every lookup of a workspace record goes through one shared helper, which treats another workspace's record as not existing. A record named in the URL then gives a 404 page saying "Page not found."; an ID submitted in a form gets that form's validation message.
- **ACC-2.5** (failure) If storage or rendering the response fails during creation, no part of the workspace, its accounts or its sample round remains, no credentials are shown, and the visitor sees a 503 page saying "Relay is temporarily unavailable. Try again later."
- **ACC-2.6** (ambiguous) A signed-in user cannot create a demo workspace: the Relay start page and the creation route redirect them to their own role home page and create nothing.
- **ACC-2.7** (adversarial) A creation request by GET, without a valid CSRF token, or whose `Origin` header names another origin, is refused and creates nothing.

## ACC-3 Limit abuse of sign-in and demo workspace creation

Failed sign-ins and demo creations are limited per client address, as defined in the [technical spec](../TECHNICAL-SPEC.md#accounts-and-workspaces), and demo creations also in total across all addresses. Each limit's window starts at its first counted request. The limits allow for peers in one lab sharing an address.

A limited sign-in shows the sign-in page, titled and headed "Sign in", with its message in place of the failure message and the form below it. The limited demo creation page shows its message as its only heading, after the [home link](platform.md#plt-4-shared-application-presentation) of PLT-4.17.

- **ACC-3.1** (boundary) The 30th failed sign-in from one client address within 15 minutes still gets the normal failure message. Any further sign-in from that address in the window, even with a correct password, gets a 429 sign-in page saying "Too many sign-in attempts. Try again later." and does not sign in.
- **ACC-3.2** (boundary) Just before a limit's window ends, its refused requests are still refused; at or after the end, they are checked normally again.
- **ACC-3.3** (ambiguous) Only failed sign-ins, including blank fields, and completed demo creations count. Successful sign-ins neither count nor reset the failed count. Refused (403, 429 or 503) requests and failed creations count toward no limit, and a refused sign-in does not extend its window. Viewing the sign-in page is never limited.
- **ACC-3.4** (boundary) The 11th demo workspace creation from one client address within 1 hour, and the 201st from all addresses within 24 hours, get a 429 page saying "Too many demo workspaces have been created recently. Try again later." and create nothing.
- **ACC-3.5** (adversarial) Varying the username or sending a forged `X-Forwarded-For` header does not escape a limit, and one address reaching its limit does not limit another address. Requests with a missing or unparseable client address share one "unknown" count instead of failing.
- **ACC-3.6** (adversarial) Concurrent creations cannot exceed a limit: with 2 demo creations left for an address, 5 simultaneous requests create at most 2 workspaces.
- **ACC-3.7** (failure) If a limit count cannot be read or recorded, including a lock or statement timeout, the request gets the 503 page from ACC-2.5, signs no one in and creates nothing.
- **ACC-3.8** (adversarial) Concurrent sign-ins cannot exceed the limit: with 1 failed sign-in left for an address, 5 simultaneous wrong-password sign-ins give at most 1 normal failure, and the rest get the 429 page.

## ACC-4 Add a Beta Tester to my workspace

A Test Coordinator can choose the "Add Beta Tester" button on Coordinator home. The creation form has no account fields. A successful action shows a page titled and headed "Beta Tester added", with "Workspace: <workspace name>", a table with columns "Role", "Username" and "Password" and one Beta Tester row, then "Save this password now. It will not be shown again."; its "Coordinator home" link precedes the heading ([PLT-4.18](platform.md#plt-4-shared-application-presentation)). The coordinator shares these credentials outside Relay. Tester password reset is a separate action under ACC-5; no invitation or retrieval of an earlier password is provided.

- **ACC-4.1** (happy) One action creates exactly one Beta Tester in the signed-in coordinator's workspace and shows its generated credentials. The coordinator stays signed in as the same account; the new credentials sign in to Tester home in that workspace. Existing accounts, rounds and results are unchanged.
- **ACC-4.2** (boundary) A workspace may have at most 10 Beta Testers, including its initial two. Adding the tenth succeeds; at 10 or more the action creates nothing and returns status 409, titled "Tester limit reached", headed "This workspace already has 10 Beta Testers." with a "Coordinator home" link. Other workspaces' accounts and the coordinator do not count toward this limit. Refusal happens before password generation when the limit is already reached.
- **ACC-4.3** (adversarial) Simultaneous actions cannot exceed the cap: with one place remaining, five simultaneous actions create at most one tester; actions that observe the filled cap receive the same 409. Each successful action has its own credentials.
- **ACC-4.4** (adversarial) Only a signed-in Test Coordinator may act. A signed-out visitor is redirected to sign-in; a Beta Tester gets the 403 of ACC-1.4. Posted fields or query parameters cannot choose a username, password, role, workspace, account or redirect target. No denied request creates an account or exposes workspace data.
- **ACC-4.5** (adversarial) Only POST is accepted; other methods, including GET and HEAD, return 405 and create nothing. A POST without a valid CSRF token or with a foreign Origin returns 403 and creates nothing. CSRF checks precede method and role checks; otherwise method checks precede sign-in and role checks.
- **ACC-4.6** (adversarial) The generated password is stored only as a hash and appears only in the successful action's response, never in later GET pages, logs, error reports, session data or cookies. Every response returned by the action, including redirects, 405, 409 and 503 responses, carries `Cache-Control: private, no-store`; middleware-generated 403 responses show no credentials. No GET route retrieves the credential response.
- **ACC-4.7** (failure) A failure in storage, password generation, committing or rendering the credential response creates no account and shows the existing 503 page from ACC-2.5 without credentials. Database lock waits and statements use the existing bounded transaction timeouts. A username collision that cannot be resolved within the existing three-draw approach also fails this way.
- **ACC-4.8** (boundary) Every successful POST is a separate creation: reloading and confirming browser resubmission can create another tester until the cap is reached. Returning to Coordinator home shows no generated password. Browser back/forward caching may redisplay a prior response despite `no-store`; Relay provides no replay, deduplication or recovery mechanism.

## ACC-5 Reset a Beta Tester's password in my workspace

A Test Coordinator chooses "Beta Tester passwords" on Coordinator home to open a page titled and headed "Beta Tester passwords". It shows "Workspace: <workspace name>", only that workspace's tester usernames, and a "Reset password" button beside each username. Before the buttons it explains: "Resetting a password stops the old password and existing tester sessions from working. Save the new password and share it with the tester outside Relay." The page's "Coordinator home" link precedes the heading ([PLT-4.18](platform.md#plt-4-shared-application-presentation)); an empty list says "This workspace has no Beta Testers."

A successful reset shows a page titled and headed "Beta Tester password reset", with "Workspace: <workspace name>", the existing "Role", "Username" and "Password" credential table containing one Beta Tester row, "Save this password now. It will not be shown again." Its links to "Beta Tester passwords" and "Coordinator home" precede the heading, in the order [PLT-4.18](platform.md#plt-4-shared-application-presentation) gives. There is no password input, email delivery or coordinator account recovery.

- **ACC-5.1** (happy) The list shows every Beta Tester in the signed-in coordinator's workspace and no coordinator or other workspace's account. Resetting a listed tester generates a new password and shows its credentials once; the new password signs in to the same Tester home. The coordinator stays signed in as the same account.
- **ACC-5.2** (boundary) A successful reset changes only the selected account's password hash. Its username, role, workspace and testing history remain unchanged; other accounts, their sessions, rounds and results are unchanged. The old password no longer signs in, and every existing session of the selected tester fails authentication on its next request, including when its old cookie is reused. Already-running requests are not cancelled.
- **ACC-5.3** (adversarial) Only a signed-in Test Coordinator may view the list or reset a password. Signed-out visitors redirect to sign-in; Beta Testers receive the 403 of ACC-1.4, before any workspace lookup. A missing or foreign-workspace target, or any coordinator target including the caller, gives the 404 of ACC-2.4. Denied requests change no password and expose no account data. Only the route's target selects the account; posted or query identity, role, workspace, password or redirect fields cannot alter the action.
- **ACC-5.4** (adversarial) The list accepts only GET and changes nothing; reset accepts only POST. Other methods, including HEAD, return 405. A POST without a valid CSRF token or with a foreign Origin returns 403 and changes nothing. CSRF checks precede method and role checks; otherwise method checks precede sign-in and role checks.
- **ACC-5.5** (adversarial) The generated password is stored only as a hash and appears only in the successful reset response, never in later GET pages, logs, error reports, sessions or cookies. Every response returned by either route, including redirects, refusals and failures, carries `Cache-Control: private, no-store`; middleware-generated 403 responses contain no credentials. No GET route retrieves a prior credential response.
- **ACC-5.6** (failure) Storage, generation, hashing, credential rendering or commit failure returns the existing 503 page from ACC-2.5 without credentials. A failed reset leaves the old password and existing tester sessions usable and preserves all account and history state. Database locks and statements use the existing bounded transaction timeouts. List storage/rendering failures also return that 503 without exposing accounts.
- **ACC-5.7** (boundary) Each successful POST resets again, including browser resubmission. Concurrent resets of one tester serialize their writes; after all complete, only the last committed password works, and sessions authenticated with an earlier password fail on their next request. There is no deduplication, replay or recovery of generated passwords. Browser back/forward caching may redisplay a prior response despite `no-store`.
